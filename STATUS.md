# Switchboard — карта и состояние

Система с нуля по дизайну `docs/designs/from-scratch/index.html`. Старая система — тег `v1`.

## Части

| папка | что | чем проверяется |
|---|---|---|
| `protocol/` | `@sb/protocol`: конверт кадра, адреса, пропуск `флот:номер:секрет`, договор-код (`request`, `frame`, схемы zod), журнал одной формы, общий клиент (`createApi`, `httpTransport`, `socketLink`) | `cd protocol && npx vitest run` |
| `platform/` | Worker `sb2-platform`: объект флота (люди, пропуска, проекты, картина, сокеты страниц) и объект машины (сокеты Host, Keeper, зрителей; доставка кадров). Вход привязки для служб — `platform/src/contract.ts` | vitest в пуле Workers |
| `services/` | Worker `sb2-services` без состояния: вход `POST /call`, сервер MCP `/mcp`, файлы страницы, проход сокетов `/f/*` и `/m/*` в платформу; модули `src/modules/<имя>/`; записи модуля — объект `Records` на модуль и флот (архив — на машину); файлы — R2 | vitest в пуле Workers |
| `host/` | Node + Claude Agent SDK: ядро (сессии, документ, связь, хранилище) и модули chat, accounts, profiles, points, proxy, shell, incidents, work, machine | vitest со стендом (поддельные SDK, связь, держатели) |
| `keeper/` | Go: служба ОС, держит Host и себя, держатели процессов | `go test` |
| `web/` | React 19 + Mantine 9 + Vite: одна страница, две раскладки; мок флота для прототипа | vitest + снимки `npm run shots` |
| `tools/` | гейт импортов, раннер проверки частей, выкладка одной командой, живая проверка флота одним списком | `node tools/test/run.mjs tools` |

## Правила для исполнителей

- Один адрес флота: всё идёт в службы (`/call`, `/mcp`, `/f/<флот>`, `/m/<флот>/<машина>`, страница); службы зовут платформу привязкой.
- Запрос описан один раз в `protocol/src/contracts/`. Новое имя — туда, с хозяином; обработчик берёт уже проверенный ввод. Договор правится только добавлением; перед правкой перечитать файл: его правят и другие.
- Модуль импортирует чужое только через `@sb/protocol` и вход пакета. Циклов нет: службы → платформа → протокол.
- Каждый запрос несёт `trace`; каждая часть на обратном пути дописывает в `reply.spans` свой отрезок `{part, ms}`; на каждый запрос — одна строка журнала (`logger` из протокола) с `type`, `from`, `to`, `ms`, `ok`, `word`, `trace`.
- Ошибка обработчика — отказ `module_failed` и строка журнала; модуль не выключается. Отказ — `throw new Refusal(слово, причина)`.
- У каждой операции предел (`within`, `CALL_MS`) и штатная остановка.
- Просто: только ожидаемые ветки; без повторов, запасных режимов и обратной совместимости.
- Язык: идентификаторы по-английски, комментарии и тексты интерфейса по-русски.
- Тесты: эталон закрепляет одно свойство на зафиксированном входе. На этой машине: запускать из пути с большой `D:/`; `setTimeout(0)` спит около 10 мс.
- Зависимости уже поставлены в корне репо. Новая зависимость — в `package.json` своей папки и `npm install` из корня (если упал — повторить: рядом могут ставить другие). `npm install-scripts approve <пакет>` — если нужен установочный скрипт.
- Свои файлы — только в своей папке. Не коммитить: коммиты делает главная сессия.
- Ресурсы Cloudflare v2 — с приставкой `sb2-`; на флот никто не выкладывает с компьютера: выкладывает CI. Секреты — из `~/.switchboard-dev/v2-cloudflare.env`, не в репо и не в argv.

Фабрика (19 нояб. 2026, дизайн — https://claude.ai/artifact/Gaq9cFkQhFfUQL1kmK7LdJ, страницы в репозитории нет; идёт по шагам): шаг 1 — часы флота. Модуль служб `clock` (`services/src/modules/clock/`): правила времени лежат в его записях — раз в срок (`at`), каждые столько миллисекунд (`every`) или по строке расписания с часовым поясом (`cron`, `tz`; без пояса — UTC); у объекта записей один будильник (`Records.wake`, `alarm`), он стоит на ближайшем сроке; срок пришёл — часы зовут хозяина вида правила (`on(вид, работа)`), следующий срок записан раньше вызова: сбой работы — строка журнала, а не повтор; пропущенное не догоняется. Вход соседям — `clock/contract.ts` (`on`, `set`, `ensure`, `drop`, `list`, `next`); своих запросов у часов нет. Первый жилец — сверка картины службы наблюдения (правило `obs.watch`, раз в минуту): её заводит первое число любой машины, дальше она идёт без запросов; когда сверка шла последний раз, говорит `obs.health` (`watched`). Эталоны — `services/src/modules/clock.test.ts`, живая проверка — `tools/fleet/live-clock.mjs`. Шаг 2 — тикет и «дать работу». Тикет — единица работы проекта: исполнитель, шаг, состояние (`ready`, `work`, `wait`, `stop`, `done`) и заметки с вердиктами; записи — объект на проект (модуль служб `factory`, `services/src/modules/factory/`), номер — `проект-число`. Инструменты `ticket_new`, `ticket_list`, `ticket_set`; во вводе номер тикета — поле `ticket` (имя `id` занято конвертом запроса). Шаг кончается вердиктом `done` (сдал), `back` (вернул, второй возврат на шаге — «стоп») или `stop`; вердикт шагу в работе даёт сессия, которая его ведёт, машина этой сессии или человек. Место у сессии-исполнителя одно и берётся одной записью; срок работы (`for`) обязателен и стоит правилом часов: вышел без вердикта — «стоп» с причиной. Службы отдают шаг машине запросом `work.give` (модуль Host `host-work`, `host/src/modules/work/`): остановленную сессию он поднимает, шаг встаёт во ввод тегом вида `ticket`; ход, взявший шаг и кончающийся без вердикта, возвращается один раз штатным хуком остановки Claude Code; записей о шагах машина не держит. Каждое движение тикета — строка истории флота `ticket` (общая строка служб — `analytics/contract.ts: line`; строку без машины видит админ). Эталоны — `services/src/modules/factory.test.ts`, `host/test/work.test.ts`; живая проверка — `tools/fleet/live-tickets.ts`. Шаг 3 — определение проекта и конвейер. Определение — файл `factory.json` в корне репозитория ролей (схема — `protocol/src/contracts/factory.ts: FactoryDef`): посты (именные постоянные сессии: машина, папка, провайдер, модель, роль, срок одного тикета), конвейеры (потолок, машины, папка с `{id}` и `{tag}`, шаги по порядку) и потолок проекта. У шага один исполнитель: свежая сессия (`session: "new"`), та же (`"same"`), пост (`post`, в имени можно `{tag}`), человек (`human`) или событие (`wait`); срок (`for`) обязателен у всякой работы сессии и у ожидания события. Применяет определение явный вызов `factory_apply {project, repo}`: службы читают файл через приложение GitHub флота (`github/contract.ts: file`), проверяют целиком (ошибки — с путём к месту в файле, отказ `bad_factory`, действует прежний коммит), открывают недостающие посты; `factory_get` отдаёт применённое определение, коммит, паузу и загрузку конвейеров, `factory_pause` — пауза: новые шаги не запускаются, идущие сдаются. Место на конвейере берётся одной записью под двумя потолками — конвейера и проекта; посту и сессии — один тикет в работе. Свежая сессия шага зовётся `проект-номер-sшаг`, машина — та из списка конвейера, где у проекта меньше шагов; тикет закрыт — свежие сессии убираются, посты остаются. «Вернул» идёт на ближайший прежний шаг с сессией, той же сессии; второй возврат на шаге — «стоп». Проверка шага (`check`) идёт на машине сессии хуком перед вызовом `ticket_set` со «сдал» (`host-work`): код не 0 — вердикт не уходит, машина записывает тикету возврат с выводом скрипта. Срок вышел — «стоп», свежая сессия шага останавливается. Проверка — команда bash на любой ОС (на Windows — Git Bash). Шаг 4 — входы по времени и отложенный тикет. Правила входа — список `on` определения: срок (`every` — «каждые 10m» или `cron` с `tz`), исполнитель (`to` — конвейер или пост), необязательная проверка-скрипт на названной машине (`check: {at, run, for, cwd}`, предел — не больше 90 с) и ключ находки (`key`, без него — имя правила). Применение определения ставит правила на часы флота (`factory/<проект>/on/<имя>`): новое и изменённое — от «сейчас», прежнее идёт как шло, снятое убирается; ближайшие сроки отдаёт `factory_get` (`next`). Срок пришёл: проверка вернула 0 — тихо, ни тикета, ни хода модели; иначе её вывод — находка: новый тикет исполнителю правила либо, пока тикет с тем же правилом и ключом открыт, заметка в него. Правило без проверки заводит тикет каждый срок. Машина проверки не ответила — не находка. На паузе правила не срабатывают. Исход каждого срабатывания — строка истории флота `rule` (`quiet`, `ticket`, `note`, `paused`, `failed`). Отложенный тикет — `ticket_new {in}`: в очередь он встаёт не раньше своего момента (разовое правило часов); так сессия ставит дело на потом и самой себе. Заметка без вердикта, пришедшая после последнего вердикта, доходит до сессии вместе с шагом. Эталоны — `services/src/modules/factory-lines.test.ts`; живая проверка в коробке — `tools/fleet/live-lines.ts` по определению из `tools/box/factory.mjs`.

Память флота (19 нояб. 2026, дизайн `docs/designs/memory`, https://claude.ai/artifact/UjsSkv5jJzSSgwJB65ZH8H): память проекта — папка `memory` кусочка профиля в общем git, штатным путём Claude Code; своего хранилища и инструментов памяти нет. Хозяин кусочков — `host-profiles` — держит одно правило записи: список пишущих моделей (`WRITERS` в `host/src/modules/profiles/profiles.ts`: Opus 5.5 и Fable 5, 5.1, 5.2) и замок — хук `PreToolUse` на `Write|Edit|MultiEdit` отказывает записи в память любого кусочка набора сессии, если модель документа сессии не из списка; модель читается на каждом вызове, поэтому смена модели действует со следующей записи и нового процесса не просит. Опции запуска от модели не зависят: папка встроенной памяти — память последнего кусочка с памятью; сессия без такого кусочка (без кусочков, с кусочками без памяти, с несобранным набором) стартует с `autoMemoryEnabled: false` — в папку машины память не пишется; настройки памяти кусочек своим `settings.json` не ставит. След — строка журнала машины `memory` уровнем «инфо» на чтение записи, запись и отказ: `callsign, model, piece, record, op` (`read` | `write` | `refused`); в историю флота идёт как любая строка (`log.query {msg: "memory"}`). Неназванную часть документа новой сессии ставит хозяин ключа по документу сессии, которая её открывает (`fill(doc, parent)`): проект — ядро, кусочки — `host-profiles`; родитель на другой машине читается одной полной строкой картины флота; пустой список `pieces: []` — без кусочков. Справка флота — третья страница `fleet://guide/memory` (три слоя, пути к сырью, правило «пишут сильные модели» без имён моделей) и одна строка в инструкциях сервера. Меру индекса памяти считает машина (`indexMeasure` в `pieces.ts`, пределы Claude Code 200 строк и 25 000 байт) и отдаёт готовой в `profile.view` (`memory`); у страницы своих пределов нет. Эталоны — `host/test/memory.test.ts`; живая проверка — `tools/fleet/live-memory.mjs` (в списке); снимок вкладки «Память» — `node docs/designs/memory/shots.mjs`. Не сделано: перенос записей из папок машин в кусочки — по слову человека; сводка следа через 14 дней и по ней отдельный дизайн отсечения и экрана «Память».
