# Switchboard — карта и состояние

Система с нуля по дизайну `docs/designs/from-scratch/index.html`. Старая система — тег `v1`.

## Части

| папка | что | чем проверяется |
|---|---|---|
| `protocol/` | `@sb/protocol`: конверт кадра, адреса, пропуск `флот:номер:секрет`, договор-код (`request`, `frame`, схемы zod), журнал одной формы, общий клиент (`createApi`, `httpTransport`, `socketLink`) | `cd protocol && npx vitest run` |
| `platform/` | Worker `sb2-platform`: объект флота (люди, пропуска, проекты, картина, сокеты страниц) и объект машины (сокеты Host, Keeper, зрителей; доставка кадров). Вход привязки для служб — `platform/src/contract.ts` | vitest в пуле Workers |
| `services/` | Worker `sb2-services` без состояния: вход `POST /call`, сервер MCP `/mcp`, файлы страницы, проход сокетов `/f/*` и `/m/*` в платформу; модули `src/modules/<имя>/`; записи модуля — объект `Records` на модуль и флот (архив — на машину); файлы — R2 | vitest в пуле Workers |
| `host/` | Node + Claude Agent SDK: ядро (сессии, документ, связь, хранилище) и модули chat, files, accounts, profiles, points, proxy, shell, work, machine | vitest со стендом (поддельные SDK, связь, держатели) |
| `keeper/` | Go: служба ОС, держит Host и себя, держатели процессов | `go test` |
| `web/` | React 19 + Mantine 9 + Vite: одна страница, две раскладки; мок флота для прототипа | vitest + снимки `npm run shots` |
| `tools/` | гейт импортов, раннер проверки частей, выкладка одной командой, живая проверка флота одним списком | `node tools/test/run.mjs tools` |

## Правила для исполнителей

- Один адрес флота: всё идёт в службы (`/call`, `/mcp`, `/f/<флот>`, `/m/<флот>/<машина>`, страница); службы зовут платформу привязкой.
- Запрос описан один раз в `protocol/src/contracts/`. Новое имя — туда, с хозяином; обработчик берёт уже проверенный ввод. Договор правится только добавлением; перед правкой перечитать файл: его правят и другие.
- Модуль импортирует чужое только через `@sb/protocol` и вход пакета. Циклов нет: службы → платформа → протокол.
- Каждый запрос несёт `trace`; каждая часть на обратном пути дописывает в `reply.spans` свой отрезок `{part, ms}`; на каждый запрос — одна строка журнала (`logger` из протокола) с `type`, `from`, `to`, `ms`, `ok`, `word`, `trace`.
- Ошибка обработчика — отказ `module_failed` и строка журнала; модуль не выключается. Отказ — `throw new Refusal(слово, причина)`.
- У каждой операции предел (`within`, `CALL_MS`) и штатная остановка.
- Просто: только ожидаемые ветки; без повторов, запасных режимов и обратной совместимости.
- Язык: идентификаторы по-английски, комментарии и тексты интерфейса по-русски.
- Тесты: эталон закрепляет одно свойство на зафиксированном входе. На этой машине: запускать из пути с большой `D:/`; `setTimeout(0)` спит около 10 мс.
- Зависимости уже поставлены в корне репо. Новая зависимость — в `package.json` своей папки и `npm install` из корня (если упал — повторить: рядом могут ставить другие). `npm install-scripts approve <пакет>` — если нужен установочный скрипт.
- Свои файлы — только в своей папке. Не коммитить: коммиты делает главная сессия.
- Ресурсы Cloudflare v2 — с приставкой `sb2-`; на флот никто не выкладывает с компьютера: выкладывает CI. Секреты — из `~/.switchboard-dev/v2-cloudflare.env`, не в репо и не в argv.

Модуль служб `clock` (`services/src/modules/clock/`): правила времени лежат в его записях — раз в срок (`at`), каждые столько миллисекунд (`every`) или по строке расписания с часовым поясом (`cron`, `tz`; без пояса — UTC); у объекта записей один будильник (`Records.wake`, `alarm`), он стоит на ближайшем сроке; срок пришёл — часы зовут хозяина вида правила (`on(вид, работа)`), следующий срок записан раньше вызова: сбой работы — строка журнала, а не повтор; пропущенное не догоняется. Вход соседям — `clock/contract.ts` (`on`, `set`, `ensure`, `drop`, `list`, `next`); своих запросов у часов нет. Первый жилец — сверка картины службы наблюдения (правило `obs.watch`, раз в минуту): её заводит первое число любой машины, дальше она идёт без запросов; когда сверка шла последний раз, говорит `obs.health` (`watched`). Эталоны — `services/src/modules/clock.test.ts`, живая проверка — `tools/fleet/live-clock.mjs`. Шаг 2 — тикет и «дать работу». Тикет — единица работы проекта: исполнитель, состояние (`ready`, `work`, `wait`, `stop`, `done`) и заметки с вердиктами; записи — объект на проект (модуль служб `factory`, `services/src/modules/factory/`), номер — `проект-число`. Инструменты `ticket_new`, `ticket_list`, `ticket_set`; во вводе номер тикета — поле `ticket` (имя `id` занято конвертом запроса). Работа над тикетом кончается вердиктом `done` (сдал), `back` (вернул, второй возврат — «стоп») или `stop`; вердикт тикету в работе даёт сессия, которая его ведёт, машина этой сессии или человек. Место у сессии-исполнителя одно и берётся одной записью; срок работы (`for`) обязателен и стоит правилом часов: вышел без вердикта — «стоп» с причиной. Службы отдают тикет машине запросом `work.give` (модуль Host `host-work`, `host/src/modules/work/`): остановленную сессию он поднимает, тикет встаёт во ввод тегом вида `ticket`; ход, взявший тикет и кончающийся без вердикта, возвращается один раз штатным хуком остановки Claude Code; записей о тикетах машина не держит. Каждое движение тикета — строка истории флота `ticket` (общая строка служб — `analytics/contract.ts: line`; строку без машины видит админ). Эталоны — `services/src/modules/factory.test.ts`, `host/test/work.test.ts`; живая проверка — `tools/fleet/live-tickets.ts`. Шаг 3 — определение проекта. Определение — файл `factory.json` в корне репозитория ролей (схема — `protocol/src/contracts/factory.ts: FactoryDef`): посты (именные постоянные сессии: машина, папка, провайдер, модель, роль, срок одного тикета), правила входа (`on`) и люди, которых зовут, когда тикет встал (`call`). Применяет определение явный вызов `factory_apply {project, repo}`: службы читают файл через приложение GitHub флота (`github/contract.ts: file`), проверяют целиком (ошибки — с путём к месту в файле, отказ `bad_factory`, действует прежний коммит), открывают недостающие посты; `factory_get` отдаёт применённое определение, коммит, паузу и очереди постов (`load`), `factory_pause` — пауза: новые тикеты не выдаются, взятые сдаются. «Вернул» возвращает тикет той же сессии; второй возврат — «стоп». Проверка «сдал» — у поста (`posts.<имя>.check`): она идёт на машине сессии хуком перед вызовом `ticket_set` со «сдал» (`host-work`): код не 0 — вердикт не уходит, машина записывает тикету возврат с выводом скрипта. Проверка — команда bash на любой ОС (на Windows — Git Bash). Шаг 4 — входы по времени. Правила входа — список `on` определения: срок (`every` — «каждые 10m» или `cron` с `tz`), исполнитель (`to` — пост), необязательная проверка-скрипт на названной машине (`check: {at, run, for, cwd}`, предел — не больше 90 с) и ключ находки (`key`, без него — имя правила). Применение определения ставит правила на часы флота (`factory/<проект>/on/<имя>`): новое и изменённое — от «сейчас», прежнее идёт как шло, снятое убирается; ближайшие сроки отдаёт `factory_get` (`next`). Срок пришёл: проверка вернула 0 — тихо, ни тикета, ни хода модели; иначе её вывод — находка: новый тикет исполнителю правила либо, пока тикет с тем же правилом и ключом открыт, заметка в него. Правило без проверки заводит тикет каждый срок. Машина проверки не ответила — не находка. На паузе правила не срабатывают. Исход каждого срабатывания — строка истории флота `rule` (`quiet`, `ticket`, `note`, `paused`, `failed`). Заметка без вердикта, пришедшая после последнего вердикта, доходит до сессии вместе с тикетом. Шаг 5, первая половина — вход по адресу с секретом и зов правила по имени. Вход у правила не больше чем один: срок, адрес (`hook: true`) или никакого; по имени зовётся любое правило — `ticket_new {on, key, text, files}`: исполнитель и название — у правила, проект машина называет сама. Адрес правилу выдаёт `hook_url` (модуль служб `hooks`, `services/src/modules/hooks/`): `/h/<флот>/<секрет>`, секрет — 32 случайных байта, в записях — его хэш; новый адрес правила отзывает прежний. `POST` на адрес — событие: тело — текст либо JSON `{key, text, files: [{name, base64}]}`; принято — 202 с номером тикета, чужой секрет — 404, отозванный — 410, правила больше нет — 404; в журнал и в историю (строка `hook`) идёт путь без секрета. Событие любого входа — одно (`factory/contract.ts: event`): открытый тикет с тем же правилом и ключом получает его заметкой, иначе заводится новый; на паузе событие не теряется — тикет ждёт в очереди. Файлы тикета (`ticket_new {files}`, файлы события) лежат в хранилище флота и встают в папку сессии, которая ведёт тикет, тем же путём, что файлы сообщения (`work.give {files}`). Вторая половина — обращения стали тикетами. Модуль машины `host-incidents`, его порт на 127.0.0.1, запросы `incident.list` и `incident.raise`, настройка флота `incidents.kinds`, вид входящего `incident`, поле `incident` строки сессии и экран «Флот → Инциденты» сняты: «событие → сессия по правилу» остаётся одно — правило входа и тикет. События самой машины зовут правило по имени в проекте сессии, с которой они случились (`protocol: MACHINE_RULES`): `account` — вход аккаунта или ключа провайдера не принят (ключ события — имя аккаунта), `model` — ответила не та модель (ключ — позывной); у сессии нет проекта или у проекта нет правила — событие остаётся строкой журнала машины. Служба компьютера шлёт событие на адрес с секретом либо скриптом с пропуском флота — `tools/send/send.mjs <адрес флота> --event <проект> <правило> <ключ> <текст…>`. Видов входящего шесть; тег `ticket` с `on` — событие правила: его текст для сессии — данные, а не команды (строки справки сервера MCP). Шаг 6 — события GitHub. Приложение GitHub флота создаётся подписанным на события о PR и ревью (адрес событий и право читать PR — в манифесте); секрет подписи называет GitHub при создании приложения, он лежит в записях модуля `github`. Приложение, созданное раньше, событий не получает (`github.app: events`). Событие приходит на `/github/<флот>` (модуль `hooks`), подпись сверяет и событие разбирает модуль `github` (`github/contract.ts: received`): не сошлась — 401; сошлась — строка истории `hook`, тикетов событие не двигает. Шаг 7, служебная часть. Что с тикетом может сделать тот, кто спросил, называют службы (`ticket_list {ticket}` → `acts`: `verdict`, `resume`, `drop`, `assign`) — тем же правилом, каким отказывает запись; страница его не повторяет. Справка сервера MCP — страница `fleet://guide/factory`: тикет и вердикт, ждать и передать, заметки, пост, определение, правила входа; в инструкциях сессии — строки о тикете и о том, что таймеров в сессии нет. Вопрос сессии по тикету идёт тому, кто дал задачу тикетом, — как вопрос дочери идёт родителю: службы называют его машине вместе с тикетом (`work.give {asker}`: создатель тикета — человек или сессия; у тикета правила входа — первый человек из `call` проекта), модуль разговора принимает это от соседа (`host.module("host-chat")`: `asked`). Свой таймер Claude Code в сессиях флота выключен (`CLAUDE_CODE_DISABLE_CRON=1` в окружении процесса сессии): расписание живёт в определении проекта, дело на потом — спящий тикет. Экран «Фабрика» (`web/src/screens/Factory.tsx`, раздел в навигации; дизайн `docs/designs/factory-ui`, https://claude.ai/artifact/M9Zna1AQn8qosKTVuzUQjb; адреса `/factory/<проект>`, `/factory/<проект>/backlog`, `/factory/<проект>/inputs`, `/factory/<проект>/t/<тикет>`, `/factory/<проект>/new`) — три вкладки. «Цех» — работа в ходу: первым блоком тикеты, которые ждут человека (стоп), ниже дорожки исполнителей: пост или сессия с тикетом — дорожка в одну станцию, свободные посты — ряд меток; место отдано тикетам, подробности определения — в подсказке, пустых разделов нет. «Бэклог» — тикеты без исполнителя и закрытые по дням. «Входы» — правила входа: чем срабатывают, проверка, кому идёт тикет, ближайший срок и тикет, который правило держит открытым. В шапке — переключатель паузы (на паузе шапка жёлтая); страница тикета — заметки с вердиктами и кнопки по `acts` из ответа служб; страница нового тикета возвращает экран туда, где тикет виден. Снимки и жесты на моке — `docs/designs/factory-ui/shots.mjs`, замер цеха — `docs/designs/factory-ui/measure.mjs`. Числа очередей постов экран берёт из `factory_get` (`load`), проекты с определением — одним его ответом, правил состояний не считает; слова и отображение — `web/src/lib/factory.ts`, мок с раздачей — `web/src/mock/factory.ts`, тесты — `web/src/screens/factory.test.tsx`. Эталоны — `services/src/modules/factory-lines.test.ts`, `services/src/modules/hooks.test.ts`, `host/test/accounts.test.ts`; живая проверка в коробке — «правила входа» (`tools/fleet/live-rules.ts`) по определению из `tools/box/factory.mjs`.

Рычаг аккаунта (22 нояб. 2026, дизайн `docs/designs/account-priority`, https://claude.ai/artifact/GQ9zhpcN1JH29nKQzpj58J): у аккаунта Claude три положения — выключен, по счёту, первым; рычаг один на аккаунт и действует на сессии любой модели. Хранит его служба ключей рядом с флагом запаса Fable: поле `use` (`off` | `auto` | `first`) в `keys.set` и в строке `keys.list`; машины узнают тем же кадром «ключи изменились». Настройки аккаунта — флаг запаса и рычаг — называет только список ключей: из ответа `keys.value` и из ответа машины `account.list` флаг запаса убран. Выключен — машина не берёт токен аккаунта: ни вызова сессии, ни пробы окон им не сделать; каталог моделей Claude служба спрашивает токеном включённого; идущий вызов доходит, следующий вызов сессии идёт другим аккаунтом (строка `account.moved` с причиной «аккаунт выключен»), спящая сессия привязана до своего вызова; в ожидании сброса выключенный не участвует. Первым — первый круг того же выбора по тому же счёту (`choose` в `host/src/modules/accounts/limits.ts`): новая, остывшая и упёршаяся в лимит сессия сначала выбирает среди годных «первым», тёплая остаётся на своём аккаунте; запас недели под Fable у «первым» бережётся как у всех; в строке `route` у кандидата пометка `first`. Поворот рычага — строка истории флота `account.use` от службы ключей (аккаунт — в том же поле, что у строк машин; отказ истории поворот не срывает). Экран «Флот → Аккаунты»: три положения в ряд под каждым годным аккаунтом, столбцы не пересортировываются, выключенный столбец гаснет. Проверки: эталоны выбора `host/test/accounts.test.ts` (блок «рычаг аккаунта»), служба ключей — `services/src/modules/wave.test.ts`, живая — часть `token` в `tools/fleet/live-accounts.ts` (в коробке, на двух аккаунтах-двойниках), снимки и жесты — `docs/designs/account-priority/shots.mjs`.

Пост — очередь роли (21 нояб. 2026, дизайн — https://claude.ai/artifact/5iucQQ8Tn3M84XGQSRiBWp, страницы в репозитории нет; запрос проекта на «инбоксы» закрыт правками поста и тикета, новых частей и инструментов нет). Пост — очередь роли и её постоянные сессии: `size` в определении поста — сколько сессий берут тикеты из одной очереди; зовутся имя, имя-2, имя-3 — одно правило договора (`protocol/src/contracts/factory.ts: postSessions, postOf`), службы и экран берут имена из него. Тикет посту ждёт любую его сессию (цель — имя поста), свободная берёт срочный, потом старший; тикет, который сессия уже вела (возврат, вставший, проснувшийся), ждёт её. Итог тикета — заведшему: тикет, заведённый сессией со своего тикета в работе, помнит его (таблица `parents`, поле `parent` тикета); сдан, снят или встал — в тот тикет ложится заметка от `.factory`. Заметки доходят до сессии раньше, чем она закроет тикет: при выдаче — все, которых она ещё не получала, одним блоком «Заметки к тикету (N)» (до какой заметки сессия видела, записано в тикете — `runs`, поле `seen`; предел блока — 4 000 знаков, остальное читается `ticket_list`); «сдал» сессии с заметкой, которой она не видела, один раз возвращается отказом `unread` с её текстом. Передача: сессия, которая ведёт тикет, называет ему другого исполнителя (`ticket_set {ticket, to}`) — тикет и заметки те же, строка истории — `assign` с `from: "work"`. Новые виды строки истории `ticket`: `defer` (до какого момента), `wake` (сколько стоял и чьим итогом возвращён), `unread` (сколько заметок). На машине (`host/src/modules/work/work.ts`): держит ли сессия тикет, модуль спрашивает у тикета, а не помнит по вызову инструмента — одно правило для проверки перед «сдал», напоминания в конце хода и «стопа» тикету умершей сессии; хука после вызова инструмента нет: отказ «сдал» тикет не снимает — ход без вердикта получит напоминание, спящий и переданный тикет — нет. Экран «Фабрика»: у поста на несколько сессий одна дорожка — имя очереди и лампа на каждую сессию, на плашке тикета в работе — кто его ведёт; на странице тикета — кнопка «Написать» (заметка без вердикта) и переход к тикету, с которого он заведён. Справка сессиям (`fleet://guide/factory`, инструкции сервера): ждать по тикету — усыпить его, а не заводить тикет самой себе; слово по делу чужому тикету — заметкой. Эталоны — `services/src/modules/factory-queue.test.ts` (19–28), `host/test/work.test.ts` (19, 20), `web/src/screens/factory.test.tsx`; живая проверка в коробке — «очередь поста» (`tools/fleet/live-queue.ts`) по определению второго проекта коробки из папки кусочка (`tools/box/queue.mjs`): `SB2_ONLY="очередь поста" node tools/box/box.mjs node tools/fleet/live.mjs box cli m1 m2`; снимки и жесты экрана на моке — `docs/designs/inbox/shots.mjs`.
