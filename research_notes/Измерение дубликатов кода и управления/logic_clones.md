# Поиск дублированной логики за пределами токенных клонов (Type-3, Type-4) для монорепо TS и Go

Состояние на ноябрь 2026 года. Заметки дополняют раздел 3 прежнего исследования и не повторяют его.

Классы доказательств: **[Н]** независимый замер; **[П]** замер автора или продавца инструмента; **[А]** автор оценивает собственный метод в научной работе; **[М]** мнение; **[бенч]** бенчмарк, а не реальный код.

## Какие инструменты работают на TS, TSX и Go сегодня

### Takeaway
Запустить поиск Type-3 и Type-4 на обоих языках одной командой сегодня можно только в jscpd 5.x, а также в молодом slopo. Весь академический ряд (NiCad, SourcererCC, Oreo, CCAligner, Deckard) либо не знает TS и Go, либо заброшен, поэтому в цикл агента не годится. Для графовых подходов на TS и Go готового детектора клонов не найдено: Joern даёт только граф, остальное надо писать самому.

### Cited Findings

**Поправки к прежнему исследованию**

- Утверждение «опубликованной точности у jscpd нет, чисел нет» устарело. Автор jscpd опубликовал [сравнение девяти моделей эмбеддингов](https://jscpd.dev/benchmarks/embedding-models). Числа это [П], подробности в следующем вопросе.
- Фраза прежнего метода 1 «Type-4 он не видит» верна только для `--similarity`. Режим `--semantic` [появился в 5.3.3](https://newreleases.io/project/github/kucherenko/jscpd/release/v5.3.3), 28 сентября 2026 года ([даты релизов](https://github.com/kucherenko/jscpd/releases)).
- Пороги CodeRankEmbed легко перепутать, в пересказах они идут в обратном порядке. Верно так: [0.4125 между языками, 0.6375 внутри одного языка](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md). Пара, которая не является лучшим совпадением друг для друга, должна набрать 0.7125.
- Прежняя таблица называет `--similarity` «сходством деревьев». Точнее: это [индекс Жаккара по отпечаткам поддеревьев нормализованного дерева](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md). Имена вызываемых функций и операторы сохраняются, поэтому логика с другими вызовами под порог не попадёт. Это по-прежнему Type-3, а не Type-4.
- В jscpd есть то, что прежняя работа предлагала собирать скриптом: [`--baseline-from-ref origin/main --fail-on-new-clones 0`](https://github.com/kucherenko/jscpd/blob/master/README.md) (храповик на новые клоны) и [Boundaries](https://github.com/kucherenko/jscpd/blob/master/README.md) (правило «этот код живёт только здесь», проверяется всеми тремя методами, в том числе `--semantic`, код выхода 1). Эффекта этих средств не мерил никто.

**Графы и запросы**

- [Joern](https://docs.joern.io/): Apache-2.0, активен, зрелость Go средняя, JavaScript высокая, **TypeScript в таблице не назван**. Требует [JDK 21, для Windows есть zip и `.bat`](https://github.com/joernio/joern). Режима поиска клонов в результатах не нашлось; граф придётся сравнивать своим кодом.
- CodeQL: [CLI на приватных репозиториях доступен только с лицензией GitHub Code Security](https://huggingface.co/AbdulElahGwaith/github-docs-arabic-enhanced/blob/main/data/reusables/code-scanning/licensing-note.md) (источник — зеркало документации). [Условия 2020 года](https://scancode-licensedb.aboutcode.org/github-codeql-terms-2020.html) запрещают анализ закрытого кода без лицензии.
- [Semgrep](https://github.com/semgrep/semgrep) и [Opengrep](https://github.com/opengrep/opengrep): оба LGPL-2.1 по API GitHub, активны. Это поиск по заданному шаблону, поэтому они подходят для запрета уже найденного повтора, а не для его обнаружения (вывод, не замер).

**Сравнение классических детекторов на текущем наборе**

- [Alam et al., ICSME 2025](https://arxiv.org/abs/2509.25754) [А: часть авторов сделали GPTCloneBench; Java, C, C#, Python]: девять детекторов с настройками по умолчанию. На GPTCloneBench Java у CloneWorks recall 70 % на Moderate Type-3 и 20 % на Type-4. На Python Type-4 в SemanticCloneBench — 11.1 %. Дообученный CodeBERT на Java Type-4 даёт 91 %, но по таблице II его точность около 0.51–0.54, у CloneWorks 0.93–0.97. Сопоставление столбцов восстановлено мной по значениям F1; текст статьи подтверждает лишь общий вывод: [у классических инструментов на Type-4 recall ниже, точность намного выше](https://arxiv.org/abs/2509.25754).

### Inferences
- Единственная связка, закрывающая оба языка без нового кода, такая: `jscpd --similarity` для Type-3 и `jscpd --semantic --semantic-scope same` для Type-4. dupl и similarity-ts нужны только как второе мнение на своём языке.
- jscpd за последние два месяца менял шкалу оценок: [релиз 5.4.1 предупреждает, что старые пороги и базы надо обновить](https://github.com/kucherenko/jscpd/releases), а 5.4.2 меняет смысл `--ignore-identifiers`. Версию нужно закреплять точно, иначе ряд метрики разорвётся.
- Лицензия slopo AGPL-3.0 мешает включению в продукт, но не запуску как внешней утилиты разработчика (моё прочтение, не юридический вывод).

### Gaps
- Сравнения jscpd `--similarity`, dupl и similarity-ts на одном размеченном наборе TS или Go не найдено.
- Работает ли `--similarity` на `.tsx`: документация пишет «TypeScript» и нигде не называет TSX. Проверяется одним запуском.
- Обрабатывает ли `jssrc2cpg` в Joern TypeScript, в документации прямо не сказано.
- Есть ли у Semgrep режим клонов, отдельно не проверялось.
- Детектора на графе зависимостей программы (PDG) для TS или Go не найдено. Поиск был неглубоким, поэтому это отсутствие находки, а не доказанное отсутствие.

## Честные числа точности и полноты и доверие к бенчмаркам

### Takeaway
На реальном коде TS и Go нет ни одного независимого замера. Лучшее приближение для Type-4 — собственный замер автора jscpd: при точности около 0.68 внутри языка полнота 0.38, а на широкой выборке проектов дубликатами оказались 57 % найденных пар старой модели. Заголовочные F1 выше 0.9 в литературе нельзя переносить: они либо опираются на испорченные метки BigCloneBench, либо рушатся при переписывании кода и смене набора.

### Cited Findings

**Состояние бенчмарков**

- BigCloneBench: [379 из 406 пар WT3/T4 (93.3 %) размечены ложно](https://arxiv.org/html/2505.04311v1), в исходной выборке из 386 пар 94.6 % [Н, Krinke и Ragkhitwetsagul]. **Поправка:** прежняя работа пишет 93.9 %; прочитанная версия v1 даёт 93.3 %. Согласие двух авторов — лишь умеренное, каппа 0.476; GPT-4o совпал с итогом людей на 97.0 %. WT3/T4 — это 8 498 894 из 8 915 130 пар, около 95 %. Из 179 работ 139 (77.7 %) использовали эти пары так, что вывод под угрозой. Авторы оценивают настоящий F1 таких работ примерно в 6.3 %. Для Type-1–3 набор они считают пригодным.
- Детекторы с высоким F1 на BCB не переносятся: [обучение на BCB и проверка на SemanticCloneBench дают 0.489–0.680 против 0.936–0.949](https://arxiv.org/html/2412.14739v1) [Н, препринт; ASTNN, GMN, CodeBERT].
- GPTCloneBench: [37 149 семантических пар, 19 288 ложных, из 79 928 сгенерированных](https://arxiv.org/abs/2308.13963v2), Java, C, C#, Python. Клоны породил GPT-3 из фрагментов SemanticCloneBench, а Type-1–2 отсеял [NiCad](https://arxiv.org/abs/2509.25754). Значит, форма набора зависит от одного генератора и одного фильтра. По сниппету поиска, ручная проверка приняла [62.14 % семантических клонов](https://arxiv.org/pdf/2309.06424v1.pdf). Пар Type-4 по всем языкам [около 25 тысяч](https://arxiv.org/pdf/2609.17338). Прямой критики меток GPTCloneBench не найдено.
- SemanticCloneBench: [4 000 вручную проверенных пар на четырёх языках, годится скорее для оценки, чем для обучения](https://arxiv.org/html/2505.04311v1). POJ-104 и OJClone построены на олимпиадах: «та же задача значит похоже». Go и TS ни в одном из этих наборов нет.
- [Обзор 28 работ о клонах и LLM](https://www.sciencedirect.com/science/article/abs/pii/S0950584926000856): Java в 83 %, Python в 50 % (по сниппету, страница вернула 403).

**Устойчивость к переписыванию**

[Xu et al., 2026, препринт](https://arxiv.org/html/2606.25272) [Н, бенч; Java и C]. 51 преобразование с сохранением поведения, 14 детекторов. Из 25 сочетаний с исходным F1 выше 90 % у 21 падение составило 10 пунктов и более.

| Набор, детектор | F1 до | F1 после |
|---|---|---|
| GCJ, CodeBERT | 94.06 | 19.89 |
| GCJ, GraphCodeBERT | 94.83 | 11.76 |
| GCJ, FA-AST (граф) | 99.04 | 43.50 |
| GCJ, GPT-OSS-20B | 99.24 | 73.20 |
| GCJ, Jev (LLM) | 99.75 | 91.44 |
| OJClone, GPT-OSS-20B | 93.93 | 91.94 |
| BCB, CodeBERT | 94.03 | 78.49 |
| BCB, GPT-OSS-20B | 40.60 | 40.91 |

Метки здесь унаследованы от наборов, поэтому это устойчивость распознавания, а не точность Type-4; авторы говорят об этом сами. Обученные детекторы рушатся сильнее LLM с промптом, но низкие числа LLM на BCB, скорее всего, отражают плохие метки, а не слабость модели (вывод мой; авторы причину не называют).

**LLM как судья пары**

- [Zhu et al., 2025, препринт](https://arxiv.org/pdf/2511.01176) [Н, бенч]: пять моделей, F1 до 0.943 (o3-mini) на наборах из CodeNet, на BCB среднее падение у той же модели 0.52. Более 90 % ответов совпадают во всех пяти запусках, колебание F1 меньше 0.03. Промпт меняет результат сильно: P0 даёт выше 0.8 на моделях GPT и 0.474–0.548 на других.
- [PolyHuman, ESEM 2026](https://arxiv.org/pdf/2608.23961) [Н, бенч; C++, Java, Python, код людей]: GPT-o4-mini верно распознаёт эквивалентность в 0.80–0.84 случаев, неэквивалентность в 0.83–0.93, но 0.97 на синтетическом SeqCoBench. Среднее по девяти моделям: 0.72–0.75 и 0.46–0.48. Несколько моделей почти всегда отвечают одно и то же, поэтому точность около 50 % на сбалансированном наборе обманчива. Чем сложнее задача, тем чаще неэквивалентное принимается за эквивалентное, и у модели заметна нестабильность между запусками.
- [EquiBench, EMNLP 2025](https://arxiv.org/pdf/2502.12466) [Н, бенч; Python, C, CUDA, x86-64; 2 400 пар]: лучший результат 78.0 %, на двух сложных категориях 62.3 % и 68.8 % при случайном 50 %. Простое переименование 91.2 %.
- [Marchezan et al., 2026, на рецензии](https://arxiv.org/pdf/2609.17338) [А; GPTCloneBench]: нулевой запуск DeepSeek-r1 на одной из строк таблицы даёт точность .998, recall .820, F1 .900. Обученный метод достигает F1 0.977 на C#, 0.968 на Java при обучении на Python. Метки те же, GPT-3.
- [Moumoula et al., FSE 2025](https://arxiv.org/abs/2408.04430v2) [Н, бенч; по сниппетам]: классификатор на эмбеддингах обгоняет LLM примерно на 2 пункта на XLCoST и на 24 на CodeNet, то есть на более сложных задачах.

**Точность инструментов на реальном коде**

- [Oreo, FSE 2018](https://ar5iv.labs.arxiv.org/html/1806.05837) [А; Java; 400 случайных пар на инструмент, два автора-судьи вслепую]: NiCad 99 %, CloneWorks 98.7 %, SourcererCC 97.8 %, Oreo 89.5 %, Deckard 34.8 %. Полнота на MT3: Oreo 30 %, SourcererCC 5 %, CloneWorks 3 %, NiCad 0.8 %.
- [SourcererCC, ICSE 2016](https://arxiv.org/pdf/1512.06448) [А]: те же авторы получили себе 83 %, NiCad 96 %, а Deckard [93 % при высоком пороге](https://arxiv.org/pdf/1512.06448). Разброс 83–98 % у одного инструмента показывает, что такие числа зависят от настройки и судьи.
- [Разметка точности трудоёмка и несравнима между работами](https://arxiv.org/pdf/1812.05195): авторы 2018 года не смогли запустить Oreo на своём бенчмарке.
- В [работе о MSCCD 2024 года](https://arxiv.org/pdf/2409.06176) точность NiCad на C составила 70 % [А].

**Эмбеддинги на реальном коде: единственный замер рядом с TS**

[jscpd](https://jscpd.dev/benchmarks/embedding-models) [П; Rosetta Code, 100 задач, 2 388 функций; 30 проектов, 8 667 функций; языки включают TypeScript, Rust, Python, C#, **Go не упомянут**].

| Модель | Полнота между языками | Полнота внутри языка | AUC внутри | Дубликаты среди 30 пар (14 проектов) |
|---|---|---|---|---|
| CodeRankEmbed (по умолчанию) | 0.565 | 0.380 | 0.825 | 93 % ± 5 |
| jina-v2 | 0.538 | 0.374 | 0.805 | 83 % ± 7 |
| jina-code-0.5b | 0.587 | 0.460 | 0.802 | 83 % ± 7 |
| SFR-Code-400M | 0.532 | 0.417 | 0.816 | 90 % ± 5 |
| codesage-small-v2 | 0.579 | 0.356 | 0.796 | 67 % ± 9 |

Пороги подобраны так, что точность примерно равна: 0.90 между языками и 0.68 внутри языка на Rosetta. Оговорки самого автора: 14 проектов — в основном порты; на более широкой выборке из 100 проектов доля дубликатов у jina-v2 была 57 %, а не 83 %; с CodeRankEmbed её не повторяли; 393 размеченные пары отобрала сама jina-v2. **«Рецензенты» здесь — языковые модели, а не люди**, хотя README пишет просто «reviewers». Текст обрезан на 1 024 токенах.

[Ditto](https://github.com/Kartik8Dwivedi/Ditto/tree/main/backend/eval) [П; 110 пар]: при косинусе 0.80 точность 0.852, полнота 0.945. Положительные пары взяты из собственной кластеризации, и авторы прямо называют это калибровкой, а не проверкой.

[Martinez-Gil, 2024](https://arxiv.org/html/2401.09885v3) [Н, бенч; IR-Plag, Java, плагиат как замена клонам]: Output Analysis F 0.90, эмбеддинги 0.47, PDG 0.53. Модель неизвестна, порог не назван, поэтому это слабое свидетельство; по нему лишь видно, что сравнение поведения стоит на первом месте.

### Inferences
- Для планирования на TS: внутри одного языка ложным окажется от трети до почти половины выводов, а больше половины настоящих клонов будет пропущено. Это моя оценка по точности 0.57–0.68 и полноте 0.38; числа взяты с задач Rosetta и судейства моделью, поэтому для реального кода они скорее оптимистичны.
- Падение у Zhu et al. на BCB может частично объясняться плохими метками, если в их выборку вошли пары WT3/T4; состав выборки я не проверил. Пока это не выяснено, сравнивать модели по такому падению нельзя.
- LLM-судья и обученный детектор ошибаются по-разному. Судья склонен принимать неэквивалентное за эквивалентное на сложном коде, а значит, для отбора кандидатов годится, а для приговора нет.
- Единственный надёжный способ узнать точность на этом монорепо — разметить 100–200 своих пар. Нужно два оценщика: каппа 0.476 у Krinke показывает, что даже авторы расходятся.

### Gaps
- Независимой точности и полноты для jscpd, similarity-ts, dupl и slopo на реальном коде нет ни на каком языке.
- Бенчмарка клонов на TypeScript или Go нет. В CodeNet заявлено более 50 языков, но разбивки по Go в [работе о межъязыковых клонах](https://arxiv.org/abs/2408.04430v2) я не проверил.
- Текст бенчмарка автора slopo не найден; страница PyPI не загрузилась.
- Часть чисел прошла через суммирующую загрузку. Из сырого текста PDF читались Zhu et al., PolyHuman, Marchezan et al., Deissenboeck et al., Alam et al.; из исходной разметки — README и документация jscpd. Таблица Alam et al. при извлечении сломалась, столбцы точности восстановлены проверкой F1. Снова сверять перед цитированием.

## Какие подходы находят одно правило в двух местах при разной форме кода

### Takeaway
Ни один подход не решает задачу сам. Рабочая цепочка выглядит так: дешёвый отбор кандидатов (эмбеддинги, пересечение вызовов и литералов), затем LLM-судья, затем запуск обеих функций на одних входах там, где код чистый. Запуск даёт контрпример, а не доказательство. Старый замер на Java показал, что до сравнения доходит только 28 % кода и что клоны встречаются намного чаще независимых переписываний. Агенты могут менять это соотношение, но замера нет.

### Cited Findings

**Статический отбор**

- Ограничение подхода: все статические детекторы [ищут похожее представление, а независимо написанный код на него не похож](https://wwwbroy.in.tum.de/publ/papers/iwsc09_juergens.pdf) [М с доводами, Juergens et al., IWSC 2009].
- `jscpd --semantic` [П] целится именно сюда: [«правило проверки, которое Rust-бэкенд соблюдает, а фронт Svelte повторяет»](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md). Фильтры пары: разные файлы; ни одна функция не вызывает другую по имени; взаимно ближайшие; порог; не менее 3 стандартных отклонений над фоном функции, без её 8 ближайших. Функция, похожая на многие другие, даёт не больше одной пары на язык.
- Описание вместо кода: [Ditto](https://github.com/Kartik8Dwivedi/Ditto) [П] просит дешёвую модель описать функцию без имени и эмбеддит описание, а не код. Довод: эмбеддинг кода тянет за собой синтаксис. На пяти репозиториях из 5 897 функций получилось 163 кластера, 112 конфликтов поведения, 18 подтверждено запуском. Отдельного сравнения описания с кодом нет.
- Фильтр действий [Oreo](https://ar5iv.labs.arxiv.org/html/1806.05837) [А; Java]: множество вызванных методов и полей, порог пересечения 55 % подобран по выборке. Идея переносима и смежна с пересечением вызываемых из [RepoReuse](https://arxiv.org/html/2609.35357), уже внесённым в прежнюю таблицу. Полнота на MT3 30 % против 5 % у SourcererCC.
- Проверка места: [Boundaries](https://github.com/kucherenko/jscpd/blob/master/README.md) проверяет не «есть ли дубли», а «есть ли этот метод вне своего места». Это прямо ложится на вопрос о владельце понятия, но требует, чтобы владелец был назван заранее.

**Поведение: запуск двух функций**

- [Deissenboeck et al., CSMR 2012](https://arxiv.org/pdf/1801.06107) [Н; Java, 5 открытых систем, 9 877 методов]. Случайные входы, отпечаток выходов, сравнение.
  - До сравнения доживает [около 28 % кусков](https://arxiv.org/pdf/1801.06107). Сгенерировать входы не удалось для 20–65 % методов (в Freemind при поблочном разбиении для 94 %). 60–87 % кусков используют типы проекта. Вызовы I/O, сети, SQL или UI затрагивают до 24 % методов.
  - Найдено 153 похожих по поведению метода и 294 куска при разбиении по смыслу. Прогон одной системы занял 1–30 часов.
  - Ложные срабатывания — функции, совпавшие на тривиальных входах вроде `null` или пустой строки. Настоящие находки часто оказывались просто делегатами.
  - Клонов, отсеянных на входе, в 17 раз больше, чем найденных совпадений поведения. 41 % совпадений нашёл бы и детектор Type-3. Вывод авторов: **искать такое стоит только после удаления обычных клонов**.
  - Контрольный набор из 109 реализаций одного задания: 105 совпадений при методах и 418 при кусках, то есть на чистом алгоритмическом коде подход работает.
- [SLACC, ICSE 2020](https://arxiv.org/pdf/2002.03039) [А; Google Code Jam, не реальные проекты]: кластеризация функций по выходам на общих входах. Java: 19 188 функций, точность 86.7 % против 30.7 % у HitoshiIO, в шесть раз больше кластеров. Python: 17 215 функций, 87.3 %. Между Java и Python: 32 кластера, 94.1 %.
- [HyClone, 2025, препринт](https://arxiv.org/html/2508.01357) [А, бенч; Python, 16 входов, сравнение только с прямым LLM]: F1 растёт с 0.11–0.59 до 0.62–0.64, recall 0.81–0.85, **а точность 0.49–0.51, то есть уровень монеты**, если набор сбалансирован. Входы пишет LLM. Побочные эффекты не обсуждаются.
- [Ditto](https://github.com/Kartik8Dwivedi/Ditto) [П]: единственный найденный инструмент такого рода на TS. Песочница на `worker_threads` и `vm`, без сети и файлов, таймаут 1 с. Запускает только чистые функции, остальное помечает как предсказанное расхождение. Показал расхождение трёх семейств: обрезка текста, разбор денег, проверка email.
- Важный сдвиг цели: Ditto показывает, что полезный результат часто не «одно и то же», а **«почти одно и то же, но на входе 17 расходится»**. Именно такой дубль опаснее всего.

**Символьная эквивалентность и входы на TS и Go**

- Работы есть для других языков: [RustAssure](https://arxiv.org/html/2510.07604v1) сравнивает C и Rust символьно, [EnsLLM](https://arxiv.org/html/2503.15838v1) использует CrossHair на Python. Для TS и Go инструмента в цикле агента не найдено.
- [`go test -fuzz`](https://go.dev/doc/security/fuzz/) принимает только `string`, `[]byte`, числа и `bool`; один тест за запуск; структуры надо собирать внутри цели.
- [Опрос подходов к тестированию с LLM, 2026](https://arxiv.org/pdf/2609.12012): расхождение даёт конкретный контрпример, совпадение на выборке оставляет поведение неизвестным.

### Inferences
- Парсер, написанный дважды, — лучший случай для такого запуска: чистая функция, строка на входе, структура на выходе, а Go-фаззинг строку принимает напрямую. Если копии на разных языках, общий корпус входов прогоняется с каждой стороны, и сравнивается нормализованный JSON. Нигде не измерено.
- Проверка с разными ветками — тоже хороший случай, но здесь расхождение бывает законным: разные контексты требуют разных правил. Значит, итогом должен быть вопрос к владельцу понятия, а не автоматическое слияние.
- Вывод Deissenboeck о частоте относится к людям и Java 2012 года. Замер [RepoReuse](https://arxiv.org/html/2609.35357) (цепочки с повторной реализацией растут с 13.8 % до 50.8 %) говорит, что доля независимых переписываний у агентов может быть намного выше, но прямого сравнения нет.
- В коде с большим количеством I/O и типов проекта запускаемой окажется малая часть, порядка той же четверти или меньше. Целями стоит брать чистые функции: разбор, проверки, вычисления (вывод; на этом коде доля не измерена).

### Gaps
- Нет ни одного замера, сколько логических дублей находит каждый подход на одном и том же реальном коде, особенно на коде агентов.
- Нет исследования, сравнивающего эмбеддинг описания с эмбеддингом кода на независимых метках.
- Точная цифра [Juergens et al., CSMR 2010](https://bibtex.github.io/CSMR-2010-JurgensDH.html) о том, что находят детекторы клонов в независимых реализациях, не подтверждена: полный текст не прочитан.
- Сниппет про Eq@DFuzz [дал 22.41 %](https://arxiv.org/html/2602.15761v1), а прежняя работа — 21.65 % (202 из 933). Расхождение не разобрано.

## Что можно дёшево прогонять на каждое изменение

### Takeaway
В цикл агента сегодня годятся токены и деревья: они работают за доли секунды или секунды, а `jscpd --changed` сравнивает изменённые файлы со всем проектом. Эмбеддинги годятся, если кэш векторов пересчитывает только изменённые функции, но измеренной задержки на репозитории среднего размера нет. Запуск поведения и LLM-судья стоит запускать только на новых парах, а не на всём коде.

### Cited Findings
- [`jscpd --changed .`](https://github.com/kucherenko/jscpd/blob/master/README.md): берёт файлы из `git status`, сравнивает с целым проектом, помечает новые клоны. `--changed-only` сравнивает только изменённые между собой. Это срез отчёта, а не инкрементальный индекс: [про кэш для токенных проходов документация молчит](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md).
- [`--baseline-from-ref origin/main --fail-on-new-clones 0`](https://github.com/kucherenko/jscpd/blob/master/README.md) сканирует дерево базовой ссылки с той же настройкой. Без файла базы, но работа удваивается.
- [`--semantic`](https://github.com/kucherenko/jscpd/blob/master/README.md): кэш векторов, второй запуск эмбеддит только функции с изменённым кодом. Демо-набор занимает [6 секунд с jina и 8 с CodeRankEmbed](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md) [П]. Размера демо в этом числе нет.
- [`--similarity`](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md): поиск точный, индекс по редким отпечаткам, большинство пар не сравнивается вовсе [П, без чисел].
- [jscpd-rs](https://vv-bogdanov.github.io/posts/fast-duplicate-code-detection-for-agents/) [П, автор форка]: Next.js 0.27 с против 14.98 с у старого jscpd, Prometheus (Go) 0.08 с против 4.84 с. Сравнение с JS-версией, а не с движком Rust в jscpd 5, и только токены.
- [slopo](https://github.com/rafal-qa/slopo): `slopo index` и `slopo embed` после изменений, локальная база; смена модели требует полной переиндексации.
- [Ditto](https://github.com/Kartik8Dwivedi/Ditto) [П]: описания кэшируются по хэшу тела. Инкрементальная переиндексация пока в планах. Цена: около ₹232 на 2 870 функций и заявленная ₹1 на PR.
- Академическая линия: [CCDetect-LSP, магистерская работа, Осло, 2023](https://www.duo.uio.no/handle/10852/103797?show=full) — инкрементальный алгоритм для IDE [А]; [Doi et al., 2019](https://ceur-ws.org/Vol-2511/QuASoQ-03.pdf) — минус 91 % времени за счёт двух стадий на CCFinder [А]; [LIICD](https://github.com/topics/code-duplication?o=desc&s=stars) — последнее обновление июль 2020.
- [Teamscale](https://teamscale.com/features/incremental-code-analysis) [П]: коммерческий анализ каждого коммита.
- [Deissenboeck](https://arxiv.org/pdf/1801.06107): 1–30 часов на систему на Java и оборудовании 2012 года, поэтому поведенческий поиск по всему коду как шаг на изменение не годится.

### Inferences
Порядок дешевизны для цикла агента, от дешёвого к дорогому (вывод из источников выше, задержек на этом монорепо никто не мерил):

| Шаг | Когда | Что даёт | Ожидаемая цена |
|---|---|---|---|
| `jscpd --changed` + `--similarity` | Каждая правка или коммит | Новые Type-1–3 | Секунды |
| `jscpd --semantic` с кэшем | Каждый коммит или PR | Кандидаты Type-4 | Только изменённые функции плюс сравнение |
| LLM-судья на новых парах | PR | Отсев очевидного | Токены на пару |
| Запуск пары | Только чистые функции, подтверждённые судьёй | Контрпример | Секунды на пару, но нужен код обвязки |

- Гейт по числу клонов лучше строить на новых, а не на всех: это уже есть в jscpd и совпадает с выводом прежней работы об итоге против счётчика.
- Агенту стоит показывать не сырой список кандидатов: при точности 57–68 % внутри языка он получит много шума, а [зачистка по детектору уже показала вред](https://arxiv.org/html/2605.07001v2).

### Gaps
- Нет измеренной задержки `jscpd --semantic` на репозитории масштаба сотен тысяч строк на CPU. Запуск на своём коде закрывает вопрос за один прогон.
- Нет данных, снижает ли обратная связь от детектора Type-3 или Type-4 новые дубли в сессии агента. [Автор jscpd-rs](https://vv-bogdanov.github.io/posts/fast-duplicate-code-detection-for-agents/) заявляет это как довод, а не как эксперимент.

## Пороги, минимальные размеры и классы ложных срабатываний

### Takeaway
Единого порога нет: значения по умолчанию лежат на 0.8–0.85 сходства и 50–100 токенах, а настройки по умолчанию работы признают плохими. Функции на 10–40 токенов почти все инструменты просто не видят, и исследования о них не найдено. Известные классы ложных срабатываний: связанный, но не дублирующий код (клиент и эндпоинт, реализации одного интерфейса, делегаты), похожее по форме с разным смыслом, тесты, сгенерированный код. Про JSX и конфигурацию замеров нет.

**Как выбирать порог**

- Настройки по умолчанию дают [неоптимальный результат](https://mhepaixao.github.io/homepage/files/esem24clone.pdf) [Н]. Многоцелевой поиск улучшает их на 71.08 % и 46.29 % по двум метрикам [А]. Но оптимизация согласия инструментов [завышает или занижает число клонов](https://discovery.ucl.ac.uk/id/eprint/1507981/) [Н, 14 релизов Mockito; прирост согласия 19.91–66.43 %]. Значит, цель настройки нельзя делать простым согласием детекторов.
- В Type-3 [нет согласия о минимальном сходстве](https://seal-queensu.github.io/publications/pdf/SANER-Iman-2015.pdf); рост порога поднимает точность и снижает полноту. Единый порог плохо подходит разнородным данным; подход без порога дал [F-меру на 12 % лучше](https://arxiv.org/pdf/2002.05204) (по сниппету) [А].
- Эмбеддинги нельзя настраивать одним числом для всех моделей: у jscpd [порог внутри языка от 0.5625 до 0.925](https://jscpd.dev/benchmarks/embedding-models). Шкала зависит от модели, и порог внутри языка всегда выше: код одного языка похож сам на себя.
- Модель без калибровки в jscpd получает [0.6 и 0.75 и предупреждение](https://newreleases.io/project/github/kucherenko/jscpd/release/v5.3.3).

**Малые функции (10–40 токенов)**

- `--semantic` видит функции только [из тех, что проходят `--min-tokens` и `--min-lines`](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md), то есть по умолчанию от 50 токенов и 5 строк.
- jscpd обходит это только в `--compare`: [короткую функцию, которую модель не может разместить, связывает по совпадению имени](https://github.com/kucherenko/jscpd/blob/master/README.md) при достаточно похожем коде.
- Группа похожих мелочей сворачивается: [десять копий геттера — девять клонов, а не сорок пять](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md).
- Ослепление имён на малых кусках опасно: релиз 5.4.2 [исправил случай, когда `x = x + x * x` считалось клоном `d = a + b * c`](https://github.com/kucherenko/jscpd/releases). Теперь имя должно соответствовать одному имени с другой стороны.
- У dupl [значения узлов не учитываются вообще](https://github.com/mibk/dupl), поэтому `if a == 13 {}` и `if x == 100 {}` равны. На малых порогах это прямая дорога к шуму (вывод).

### Inferences
- Для функций на 10–40 токенов лучше работает не сходство, а точное равенство нормализованного дерева или хэша тела: при малом размере похожесть теряет смысл, а совпадение полностью остаётся значимым. Пример `--min-tokens 30 --min-lines 3` есть в [README](https://github.com/kucherenko/jscpd/blob/master/README.md), но его последствия не измерены. Сюда хорошо подойдёт `--similarity=1` с пониженным `--min-nodes` (моё предложение, не проверено).
- Для Go ждать шума от шаблона обработки ошибок логично, потому что dupl считает только типы узлов, но я не нашёл ни одного источника, где это измерено. В jscpd имена вызываемых сохраняются, поэтому его режим должен страдать меньше (вывод).
- Порог для своего кода стоит выбирать по размеченной выборке пар: брать 0.8 как старт, смотреть, сколько пар настоящие на 0.7, 0.8, 0.9. Число не переносится между проектами, инструментами и версиями.

### Gaps
- Исследования минимального размера клона и порога на функциях 10–40 токенов не найдено ни в одной работе.
- Замера ложных срабатываний на деревьях JSX не найдено; jscpd лишь [считает элемент JSX вызовом компонента](https://github.com/kucherenko/jscpd/blob/master/docs/rust.md).
- Замера по конфигурации и таблицам данных не найдено.
- Полный текст [Tiarks et al., 2011](https://dblp.uni-trier.de/rec/journals/sqj/TiarksKF11.html), классической работы о том, какие Type-3 люди считают настоящими, не прочитан. Сюда же относится текст работы [Multi-threshold token-based code clone detection](https://arxiv.org/pdf/2002.05204).
