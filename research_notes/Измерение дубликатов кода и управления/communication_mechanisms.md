# Измерение дублированной коммуникации и дублированных механизмов в распределённой системе

Состояние на ноябрь 2026. Целевая система: Cloudflare Workers, Durable Objects, процесс Node, браузерные приложения; JSON-кадры с полем `type` по WebSocket и HTTP POST; структурные JSON-журналы.

Метки доказательности: **[независимое]** — измерили не авторы инструмента; **[авторы]** — измерение авторов инструмента или вендора; **[бенчмарк]** — синтетическая или учебная система; **[мнение]** — практик, блог, документ без измерения. Пометка «(сниппет)» значит, что полный текст не читался, цифра взята из реферата или поисковой выдержки.

## Обнаружение анти-паттернов и запахов микросервисов (статика и рантайм)

### Takeaway
Готового инструмента для стека TS/Go нет: все инструменты с опубликованными числами сделаны под Java/Spring или этого не опровергают. Запах «chatty» нет ни в одном из проверенных списков детекторов, а заявленная точность сильно падает при перепроверке. Переносятся не инструменты, а определения запахов и графовые проверки, которые считаются на своём графе за один вечер.

### Cited Findings

Каталог и зрелость области:
- Третичное исследование свело 203 анти-паттерна из семи обзоров к 58 непересекающимся в пяти категориях; термины в обзорах расходятся, а инструментов поддержки разработки авторы называют недоступными. **[независимое, обзор]** — [Cerny et al., JSS 2023](https://oulurepo.oulu.fi/handle/10024/44035) (сниппет)
- В обзоре рантайм-инструментов самый упоминаемый анти-паттерн — циклические зависимости. **[независимое, обзор]** — [Visualizing Anti-Patterns at Runtime](https://www.researchgate.net/publication/367048021_Visualizing_Anti-Patterns_in_Microservices_at_Runtime_A_Systematic_Mapping_Study) (сниппет)

Инструменты:
- **MSANose**: заявлено 11 запахов, это библиотека Spring Boot с `pom.xml` и Lombok, вход — путь к скомпилированным сервисам; README перечисляет 10 проверок (unversioned API, shared libraries, wrong cuts, cyclic dependency, shared persistency, ESB, no API gateway, inappropriate service intimacy, too many standards, greedy microservices); в репозитории 6 коммитов. — [github.com/cloudhubs/msa-nose](https://github.com/cloudhubs/msa-nose)
- MSANose проверен авторами на Train Ticket и Teacher Management System; в реферате слово «accurately» без чисел точности. **[авторы, бенчмарк]** — [запись NSF PAR](https://par.nsf.gov/biblio/10310336-automated-microservice-code-smell-detection), [Applied Sciences 2020](https://par.nsf.gov/biblio/10203757-automated-code-smell-detection-microservices-through-static-analysis-case-study)
- **Arcan**: изначально анализ скомпилированной Java; подтверждён разбор Java, C и C++; поддержка TS и Go в найденных источниках не подтверждена. — [страница проекта](https://essere.disco.unimib.it/wiki/arcan/), [промышленный кейс 2022](https://arxiv.org/pdf/2203.08702)
- Расширение Arcan для микросервисов (TechDebt '20) ищет три запаха: Cyclic Dependencies, Hard-Coded Endpoints, Shared Persistence. — [реферат в профиле автора](https://it.linkedin.com/in/ilaria-pigazzini) (вторичный источник; есть ли это в текущем выпуске, не подтверждено)
- **MARS** (Tighilt et al., JSS 2023): 16 анти-паттернов, 24 системы, средняя precision 82 %, recall 89 % по ручной проверке. **[авторы]** — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0164121223001504) (сниппет)
- Перепроверка MARS против ChatGPT 5.2, Gemini 3 Pro и Qwen 3.5 Plus на 13 репозиториях показывает другую картину по отдельным запахам: Hard-Coded Endpoints — recall MARS 40 % против 93 % у ChatGPT; Nano-service — recall MARS 0 %; Cyclic Dependencies не нашёл никто (у всех трёх LLM 0 %/0 %, MARS тоже не нашёл). Вывод авторов: LLM «not yet a replacement», но полезное дополнение; статика сильнее там, где нужны межсервисные связи. Эталон разметки взят из исходной работы MARS, авторы сами называют это угрозой; статистических тестов нет. **[независимое, малая выборка]** — [arXiv 2606.26927](https://arxiv.org/html/2606.26927)
- В том же исследовании перечислены все 16 запахов MARS: Wrong Cuts, Cyclic Dependencies, Shared Libraries, Shared Persistence, Mega-service, Nano-service, No API Versioning, Hard-Coded Endpoints, No API Gateway, Time Outs, No Health Check, Manual Configuration, No CI/CD, Multiple Service Instances Per Host, Local Logging, Insufficient Monitoring. Chatty среди них нет. — [arXiv 2606.26927](https://arxiv.org/html/2606.26927)
- **DAMP** (JSS 2026): заявлено 93 % precision и 97,9 % recall на 15 анти-паттернах и 25 системах, превосходство над существующими инструментами. **[авторы]** — [ScienceDirect](https://www.sciencedirect.com/science/article/abs/pii/S0164121226001846) (только сниппет, страница закрыта)
- **MicroPAD**, LLM-поиск паттернов инфраструктуры: 49,6 % precision и 32,8 % recall. **[авторы]** — [arXiv 2603.23073](https://arxiv.org/pdf/2603.23073) (сниппет)

Измеримость самого запаха:
- Hub-like: на 25 сетях микросервисов детекторы хабов почти не согласуются (каппа Флейсса 0,10 по входящим связям, 0,065 по исходящим, 0,042 по всем); сети не безмасштабные; лучшим оказался метод Кирклая с кодированием Эрдёша—Реньи, а подход Arcan авторы предлагают заменить. **[независимое]** — [Bakhtin et al. 2025](https://arxiv.org/abs/2506.07683)
- Там же recall признан невычислимым: разметки нет, а понятие Hub-like субъективно. — [arXiv 2506.07683](https://arxiv.org/pdf/2506.07683)

Рантайм:
- Hübener et al. (ICSE-SEIP 2022, стр. 75–76): метод и инструмент поиска анти-паттернов по распределённым трассам, промышленный кейс, соавтор из ING. Какие именно анти-паттерны — в доступной части не названо. **[авторы]** — [TU/e](https://research.tue.nl/en/publications/ab106dbd-fe8c-499c-afd5-b2268cd95cc5), [researchr](https://researchr.org/publication/HubenerCLVKL22)
- Диплом TU Delft о том же на данных ING: метрики из трасс объединяются в вероятность анти-паттерна, есть опрос сопровождающих. — [TU Delft](https://repository.tudelft.nl/file/File_4d60a6c1-3eb0-4e36-8243-54bf7ec05de1) (сниппет, полный текст не открылся)
- Единственное найденное правило для chatty — эвристика из блога: один и тот же вызов пять и более раз в одной трассе. Порог не обоснован. **[мнение]** — [OneUptime](https://oneuptime.com/blog/post/2026-02-06-optimize-microservice-communication-opentelemetry/view)

### Inferences
- Для TS/Go переносимы проверки, а не инструменты. Цикл, хаб, shared persistence и wrong cut — это запросы к графу «модуль → модуль» и «модуль → хранилище», а граф у системы с кадрами `type` строится проще, чем у REST-системы на Spring: тип кадра уже является именем ребра.
- Цифрам precision/recall из статей авторов доверять нельзя: разрыв между средним MARS 82/89 и отдельными значениями 60/40 и 0 recall показывает, что среднее скрывает провалы именно на межсервисных запахах.
- Абсолютные пороги хаба и chatty переносить нельзя: каппа около 0,1 означает, что «хаб» зависит от выбранного детектора. Пригоден только относительный показатель — изменение числа между сборками.

### Gaps
- Не найдено инструмента с заявленной поддержкой TypeScript или Go для анти-паттернов микросервисов. Подтвердить языки MARS и DAMP не удалось: статьи и реплика этого не называют, косвенные признаки (pom.xml, application.yml) указывают на Java/Spring.
- Не найдено измеренной точности обнаружения chatty services ни в одной работе.
- Не удалось проверить, какие анти-паттерны определяет работа Hübener et al.

## Построение настоящего графа коммуникаций: код, трассы, журналы, process mining

### Takeaway
Для системы с кадрами `type` лучший первый источник — собственный статический реестр «тип кадра → кто шлёт, кто принимает», затем проекция существующих JSON-журналов в журнал событий; трассы Cloudflare пока не покрывают WebSocket и не склеиваются с внешними процессами. Process mining умеет считать повторы и варианты пути, но работы, где он находит избыточные переходы в потоках сообщений, не найдено: метод применим, доказательств нет.

### Cited Findings

Из кода:
- Обзор инструментов восстановления архитектуры: найдено 13 статических инструментов, запустить удалось 9; лучший одиночный F1 — 0,86, комбинация четырёх — 0,91. Отчёт зарегистрирован на MSR'24. **[полунезависимое: первый автор — автор победившего Code2DFD]** — [Schneider et al.](https://arxiv.org/abs/2412.08352)
- По связям между сервисами из восьми инструментов только три годятся: Code2DFD F1 0,87, MicroDepGraph 0,67, Attack Graph Generator 0,54; три не нашли ни одной связи, Prophet 0,02, RAD-source 0,04. Набор — приложения на Java со Spring, небольшие и однородные, что авторы называют главной угрозой обобщению. — [полный текст](https://arxiv.org/pdf/2412.08352)
- Единственная попытка независимости от языка, Prophet2 с language-agnostic AST, не собралась, документации нет, разработчики ушли из науки. — [там же](https://arxiv.org/pdf/2412.08352)
- Метод почти всех таких инструментов: найти конечные точки сервиса, затем места вызова, сопоставить. — [обзор статических подходов](https://www.researchgate.net/publication/393553219_Static_Approaches_in_Microservice_Architecture_Recovery_-A_Survey) (сниппет)
- Ближайший аналог кадров с типом — **ROSDiscover** для ROS (типизированный pub/sub с поздним связыванием): строит модели компонентов из исходников, соединяет их по конфигурации, проверяет правила первого порядка. Доля восстановимых вызовов API 87,37 %, недоприближение 9,09 %, переприближение 6,82 %; поймал 8 из 19 реальных ошибок конфигурации (42 %); ложных срабатываний 8, 5 и 2 на трёх системах. **[авторы]** — [ICSA 2022](https://zenodo.org/records/5834633/files/paper.pdf)
- **RADAR** для Node.js строит event-based call graph, потому что обычный граф вызовов не видит поток через подписку и emit. Находит dead listener (подписка на событие, которое не шлют) и lost event (emit с опечаткой или не на тот объект). — [Madsen, Tip, Lhoták, OOPSLA 2015](https://plg.uwaterloo.ca/~olhotak/pubs/oopsla15.pdf)
- Метод RADAR не масштабируется: число контекстов может расти экспоненциально; продолжение заменяет его статистикой по корпусу. **[авторы: Tip — соавтор обеих работ]** — [Arteca, Schäfer, Tip](https://arxiv.org/pdf/2107.13708)

Из трасс:
- `servicegraph` connector OpenTelemetry: статус alpha; ребро — пара client/server или producer/consumer; метрики `traces_service_graph_request_total` и др. с метками `client`, `server`, `connection_type`; пара ждёт в памяти, TTL 2 с, `max_items` 1000; все спаны запроса должны прийти на один экземпляр. — [README](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/connector/servicegraphconnector/README.md)
- Workers tracing: early beta; автоматически покрыты fetch, привязки KV, R2 и Durable Object, RPC до Durable Object, обработчики fetch, scheduled, queue; WebSocket на странице не упомянут; хранение 7 дней; с 1 декабря 2026 учитывается в цене Observability. — [Cloudflare](https://developers.cloudflare.com/workers/observability/traces/)
- Идентификаторы трасс не передаются за пределы Cloudflare, W3C Trace Context обещан; операции без I/O могут показывать 0 мс. — [known limitations](https://developers.cloudflare.com/workers/observability/traces/known-limitations/)
- Соглашения OpenTelemetry для сообщений: контекст создаётся продюсером и передаётся потребителю, связь через span links; статус в просмотренной версии Experimental. Про WebSocket ничего нет. — [messaging-spans](https://github.com/open-telemetry/semantic-conventions/blob/main/docs/messaging/messaging-spans.md)
- На масштабе Meta (более 12 млн экземпляров, более 180 тыс. рёбер) многие пути обрываются из-за лимитов, потерь записей и неинструментированных служб, причём глубокие пути обрываются непропорционально чаще. **[производство, соавтор из Meta]** — [Huye et al., ATC '23](https://www.usenix.org/conference/atc23/presentation/huye), [разбор](https://muratbuffalo.blogspot.com/2023/12/lifting-veil-on-metas-microservice.html)
- Открытые трассы Alibaba выбраны с частотой 0,5 %, а анализ ICPE 2024 нашёл несогласованности, мешающие собрать полные трассы. — [обзор наборов](https://www.abhishek-tiwari.com/distributed-traces-of-microservices-architecture-publicly-available-datasets/) (вторичный)
- Service Weaver: рантайм «can construct a fine-grained call graph between components and use it to identify the critical path, the bottleneck components, the chatty components» и совместить болтливые компоненты в одном процессе. Это заявка в позиционной статье, не измерение. **[мнение]** — [HotOS '23](https://sigops.org/s/conferences/hotos/2023/papers/ghemawat.pdf)
- Service Weaver в режиме сопровождения с 5 декабря 2024, причина — мало прямого использования; репозиторий архивирован 4 марта 2026. — [github.com/ServiceWeaver/weaver](https://github.com/ServiceWeaver/weaver)

Из журналов:
- The Mystery Machine (Facebook, OSDI '14): причинная модель из уже существующих журналов; нужен минимум — идентификатор запроса, идентификатор хоста, локальная метка времени, метка события. **[авторы, производство]** — [разбор](https://muratbuffalo.blogspot.com/2015/03/the-mystery-machine-end-to-end.html); по комментарию, подход предполагает ациклический граф вызовов — [The Morning Paper](https://blog.acolyer.org/?p=1205)
- lprof: восстанавливает поток запроса только из журналов, предварительно разобрав бинарный код; precision извлечения 88 %, помог в 65 % выбранных реальных аномалий. **[авторы]** — [OSDI '14](https://www.usenix.org/conference/osdi14/technical-sessions/presentation/zhao)
- Workers Logs индексируют поля JSON автоматически, запись до 256 КБ, хранение 7 дней на платном плане и 3 на бесплатном; выгрузка — OpenTelemetry export, Logpush, Tail Workers. — [Cloudflare](https://developers.cloudflare.com/workers/observability/logs/workers-logs/)

Process mining:
- Диплом RWTH: трассы OpenTelemetry и Jaeger → журнал событий → discovery и conformance, модели Петри и BPMN, кластеризация трасс. — [RWTH](https://swc.rwth-aachen.de/theses/enhancing-software-run-analysis/)
- Taibi и Systä (2019) применили инструмент process mining к журналам рантайма, чтобы предложить разрезы монолита; проверено в промышленном проекте. **[авторы]** — [CLOSER 2019](https://scitepress.org/Papers/2019/77559/)
- DEBS 2016 о применении к распределённым приложениям: постоянные проблемы — пропущенные, несогласованные и грубые метки времени. **[авторы, практический отчёт]** — [Muthusamy et al.](https://archive.cps-vo.org/node/33133) (сниппет)
- Трасса иерархична, журнал событий табличен, поэтому нужна явная проекция. **[мнение, вендор]** — [Gravitee](https://www.gravitee.io/corpus/gen-1991/process-mining/opentelemetry-based-process-mining.html)
- Сплющивание объектных журналов даёт convergence, divergence и deficiency и порождает ложные петли, потому что смешиваются несвязанные события. — [Object-Centric Process Mining](https://www.vdaalst.rwth-aachen.de/publications/p1398.pdf), [arXiv 2303.16680](https://arxiv.org/pdf/2303.16680) (сниппеты)
- PM4Py: `discover_dfg`, `get_variants`, `get_rework_cases_per_activity` (случаи с повтором действия), `discover_ocdfg` для объектных журналов. — [зеркало документации 2.7.0](https://tessl.io/registry/tessl/pypi-pm4py/2.7.0/files/docs/statistics-analysis.md)
- PM4Py лицензирован под AGPL-3.0, есть отдельная коммерческая версия. — [GitHub](https://github.com/process-intelligence-solutions/pm4py)
- Disco: бесплатная академическая лицензия по программе университетов, публичных цен нет. — [Fluxicon](https://www.fluxicon.com/academic/)

### Inferences
- Рекомендуемый порядок для кадровой системы, без продового трафика:
  1. Статический реестр: для каждого `type` — файлы-отправители и файлы-приёмники. Отправитель без приёмника — lost event; приёмник без отправителя — dead listener. Это правило ROSDiscover и RADAR, только вместо анализа потока данных — литерал типа в коде.
  2. Динамический граф из журналов: если каждая запись несёт `type`, `id`, отправителя, получателя и идентификатор исходного действия, требования Mystery Machine выполнены. Без идентификатора исходного действия случай в process mining определить нельзя: `id` кадра живёт только пару запрос-ответ.
  3. Сверка двух графов: ребро есть в коде, но нет в журналах прогонов — кандидат на удаление; есть в журналах, но нет в реестре — неявный путь.
- Сопоставление понятий для PM4Py: case = исходное действие, activity = `type` плюс пара отправитель→получатель, timestamp — метка получателя. `get_rework_cases_per_activity` даёт петли, `get_variants` — разные пути одного действия. Два варианта с одним исходным событием и одним итогом — кандидат на второй путь. Это моя проекция, в литературе её подтверждения нет.
- Метки времени разных машин нельзя считать упорядоченными (см. DEBS 2016); порядок надёжнее брать из пар запрос-ответ и родительского кадра, чем из часов.
- Объектные журналы здесь полезнее плоских только если кадр относится к нескольким объектам (сессия и машина); начинать лучше с плоского журнала на одно действие, иначе петли окажутся артефактом сплющивания.
- Для разовой аналитики хватит собственного скрипта на Node: DFG и счётчик повторов — это группировка по case и подсчёт соседних пар. AGPL PM4Py при локальном разборе журналов не мешает, но и выигрыш от него появляется только на discovery и conformance.
- Сбор коллектора и servicegraph избыточен для малой команды: он требует подстановки контекста в кадры и держит состояние ради того же графа, что выводится из журналов.

### Gaps
- Не найдено ни одного исследования, где process mining применён для поиска избыточных переходов, петель или дублирующих путей в потоках сообщений микросервисов. Применимость — вывод, не факт.
- Не найдена работа, применяющая объектный process mining к журналам или трассам микросервисов.
- Не найдено инструкции OpenTelemetry именно для WebSocket-кадров; передача `traceparent` внутри кадра — разумное, но непроверенное решение.
- Нет данных, покрывает ли Workers tracing Hibernation API и сообщения WebSocket в Durable Object: страница об этом молчит.
- Статус ProM не проверен: поиск не вернул источника.

## Избыточность на уровне протокола: session types, хореографии, AsyncAPI/OpenAPI, неиспользуемые поля и сообщения

### Takeaway
Формальные методы доказывают безопасность протокола, а не его минимальность; единственная близкая работа — теоретическая. Практическая ценность в трёх простых вещах: схема кадров и линт неиспользуемого, проверка вложенности JSON Schema для почти-дублей, анализ чтения полей в коде. Для «ответа, который никто не читает» и «почти одинаковых кадров» готовых инструментов не найдено.

### Inferences
- Сообщения без потребителя и потребители без сообщения — самая дешёвая и надёжная проверка всего этого раздела. Для реестра типов она точнее любого линта спецификации, потому что сверяет код с кодом. Схема AsyncAPI добавила бы второе описание тех же кадров — второе место для одного знания; её стоит заводить, только если она генерируется из типов.
- Почти-дубли кадров: для каждой пары типов с похожими полями запускать проверку вложенности JSON Schema в обе стороны. Взаимная вложенность — один и тот же кадр под двумя именами; односторонняя — кандидат на слияние с необязательным полем. Схемы можно получить из типов TypeScript; это композиция, опубликованного применения именно для поиска дублей нет.
- Отсев по именам — по правилу ROSDiscover: кандидат показывается, только если совпадает и форма, и близкое имя, иначе шум.
- Мёртвые поля: для кадров, описанных типами TS, ответ даёт поиск ссылок компилятора на свойство (подход MicroProf, переведённый со слежения за памятью на статику). Динамический вариант — прокси на разобранном кадре в тестах, считающий прочитанные поля; журнал прогонов тестов заменит продовый трафик.
- «Запрос там, где хватило бы кадра» можно свести к счётчику: на стороне вызова результат `reply` никто не использует, кроме проверки успеха. Если и ошибка не обрабатывается, ответ лишний. Это выводится по тому же анализу чтения полей, но проверенного метода нет.
- Вводить session types для обнаружения избыточности нет смысла: они потребуют переписать протокол и докажут другое свойство. Глобальный тип полезен лишь как способ записать один поток на бумаге и посчитать его обмены.

## Дублирование механизмов: повторные реализации инфраструктурной роли

### Takeaway
Прямого исследования «две реализации retry, очереди или журнала в одном коде» не найдено; есть соседние работы о подражании библиотекам и об обнаружении retry. Лучший проверенный приём — WASABI: структурный шаблон плюс ключевые слова плюс LLM на контекст. Чистые клон-детекторы и LLM на семантических клонах слабы, поэтому надёжнее реестр ролей с запретом прямого использования, чем автоматический поиск сходства.

### Cited Findings

Подражание библиотекам:
- Sun, Khoo, Zhang (ICSM 2011): графы зависимостей по данным и отношение поглощения трасс; 313 подражаний импортированным библиотекам, средняя precision 82 %, и 116 подражаний статическим библиотекам, 75 %. **[авторы]** — [Waterloo](https://swag.uwaterloo.ca/publications/graph-based-detection-of-library-api-imitations.html)
- Bauer, Völke, Jürgens (2014): поиск концепта по идентификаторам плюс статический анализ между двумя наборами кода. Калибровка: из первых 250 находок 195 — потенциальные повторы (11 точных, 86 похожих, 98 по концепту), 18 плохих совпадений, причина большинства — общая лексика. ### Inferences
- Полезная форма — реестр ролей, а не детектор сходства. На роль (retry, timeout, очередь, кэш, журнал, генерация id, base64, проверка схемы) заводится одна запись: разрешённый модуль и сигнатуры прямого использования (`setTimeout` в петле с `catch`, `crypto.randomUUID`, `btoa`, `Buffer.from(..., 'base64')`, `console.*`, `JSON.parse` на границе). Вхождение вне разрешённого модуля — находка; счётчик по роли — метрика. Это гейт по устройству кода: Semgrep/Opengrep или ast-grep в TS работают внутри файла, и межфайлового анализа не требуется.
- Для ролей без однозначной сигнатуры (очередь, кэш, retry вне петли) подходит схема WASABI: шаблон выбирает кандидатов, LLM читает контекст и отсекает. Цена у авторов — единицы долларов на систему, ожидать надо ложных срабатываний на уровне одного к двум.
- WASABI отсекает polling как ложный retry: структуры похожи. Значит, один проход по петлям с задержкой находит сразу оба механизма, и разделять их надо по контексту.
- Клон-детектор ловит только копипасту. Две реализации одной роли написаны разными словами, поэтому он даст нижнюю границу, а не оценку. Лексика концепта (Bauer) тут работает лучше, и она же даёт основную ошибку: общая лексика у разных концептов.
- Для закрытого кода CodeQL без лицензии недоступен; статус лицензии нужно проверить до выбора инструмента.
- Причины из «Why Reinventing the Wheel» читаются как правило: своя реализация может быть верным решением, если от библиотеки нужна малая часть. Метрика считает две реализации внутри системы, а не отказ от внешней библиотеки.

- Не найдено открытых наборов правил Semgrep или CodeQL для этой цели; конкретные шаблоны выше — предложение, не источник.
- Все работы о подражании и WASABI — на Java; переноса на TypeScript не найдено.
- Полный текст WASABI не читался, цифры с постера.

## Метрики переходов, fan-out и сообщений на действие; связь с сопровождаемостью и инцидентами

### Takeaway
Прямых данных, что число переходов, fan-out или сообщений на действие предсказывает инциденты или стоимость сопровождения, не найдено. Сильное доказательство есть только для петель усиления нагрузки: retry поддерживал больше половины изученных метастабильных отказов. Остальные метрики годятся для сравнения системы с собой во времени, а не как порог.

### Cited Findings

Инциденты:
- 22 метастабильных отказа из 11 организаций; минимум 4 из 15 крупных сбоев AWS за десятилетие. — [Huang et al., OSDI '22](https://www.usenix.org/conference/osdi22/presentation/huang-lexiang)
- Самый частый поддерживающий эффект — политика retry, более 50 % изученных случаев (11 названных инцидентов: GGL2, GGL3, AWS1–3, AZR2, AZR4, IBM1, SPF1, SPF2, CAS2). **[независимое, публичные отчёты об инцидентах]** — [полный текст](https://www.usenix.org/system/files/osdi22-huang-lexiang.pdf)
- Перемножение retry по слоям (R в степени N) — арифметика из блогов; цифры вроде 64× или 8 % трафика в первоисточнике не найдены. **[мнение]** — [DEV](https://dev.to/speed_engineer/your-retries-are-a-load-multiplier-how-a-5-second-blip-becomes-a-40-minute-outage-17p5)
- Разбор 2 641 закрытой задачи из 15 систем (всего 2 698 случаев): Service Communication — 166 (6,15 %), Technical Debt — 687 (25,46 %), Service Design Debt — 29 (1,07 %). Это классификация задач, не связь с метрикой. **[независимое]** — [arXiv 2302.01894](https://arxiv.org/pdf/2302.01894)

Fan-out:
- Хвост при fan-out: 1 − (1 − p)^n; при p = 1 % и n = 100 медленными будут 63 % запросов. Арифметика Dean и Barroso, пересказ. — [разбор](https://aboutcomputingsystems.substack.com/p/paper-pursuit-5-the-tail-at-scale)
- Эксперимент на µBench: шесть топологий, 5–20 сервисов, одинаковая нагрузка; Mesh худшая по пропускной способности, задержке и отказам; Mesh и Chain до 39,13 кДж; при 20 сервисах пропускная способность сходится к 8–9 rps, потому что насыщение стирает структуру. **[бенчмарк, синтетика]** — [Ristova, Stoico 2026](https://arxiv.org/pdf/2604.00080)
- Train Ticket: Clique и Blob встречаются вместе, высокая связность даёт заметно худшие оценки производительности; сильная корреляция со значениями связности. **[бенчмарк]** — [Avritzer et al., ICSA 2025](https://cs.gssi.it/catia.trubiani/download/2025-ICSA-Correlation-Architecture-Performance-Antipatterns.pdf)
- Пять бенчмарк-систем: архитектуры с плохой сложностью показывают худшую производительность. **[бенчмарк]** — [Avritzer et al., JSS 2026](https://cs.gssi.it/catia.trubiani/download/2026-JSS-Automated-Assessment-Relationship-Microservice-Architectures-Performance.pdf)

Описательные данные:
- Meta: трассы широкие и мелкие; идентификатор входа предсказывает набор потомков в 50 % и более выполнений, но плохо предсказывает число RPC. **[производство, соавтор из Meta]** — [разбор ATC '23](https://muratbuffalo.blogspot.com/2023/12/lifting-veil-on-metas-microservice.html)

- Эти работы описывают форму графа и не связывают её с качеством.

Связность и сопровождаемость:
- Статья о структурной связности: проверенных метрик фактической связности сервисов нет; в перечне — число синхронных зависимостей и самая длинная синхронная цепочка; проверка на 17 открытых проектах. — [CLOSER 2021](https://www.scitepress.org/Papers/2021/104819/pdf/index.html)
- Зарегистрированный отчёт о логической связности в микросервисах: эмпирических данных о слабой связности мало. — [arXiv 2306.02036](https://arxiv.org/pdf/2306.02036)
- Сравнение статической и взвешенной динамической связности: четыре эксперимента по четыре недели на коммерческой системе; неожиданно высокая корреляция; динамические меры не заменяют статические как показатель сопровождаемости. Уровень классов и пакетов, не сервисов. **[независимое, производство]** — [Schnoor, Hasselbring 2020](https://arxiv.org/abs/1909.12521)
- Cadmatic, ICSA 2026: в двух монолитах структурная связность слабо коррелирует с другими, логическая и организационная — сильно. **[независимое, промышленное]** — [ICSA 2026](https://conf.researchr.org/details/icsa-2026/icsa-2026-software-architecture-in-practice-track/11/Software-Coupling-Metrics-An-Industrial-Evaluation-at-Cadmatic) (сниппет)
- Архитектурные запахи Arcan, 31 система на Java: в 87 % коммитов больше изменений в артефактах с запахом, частота изменений растёт после появления запаха, изменения крупнее. Это не микросервисы; результаты по дефектам в этой работе не подтверждены. **[авторы: в соавторах создатели Arcan]** — [Sas et al., 2022](https://zendy.io/title/10.1002/smr.2398) (сниппет)
- Метод отслеживания связности в рантайме по выпускам проверен на искусственных данных. **[бенчмарк]** — [SBCARS](https://sol.sbc.org.br/index.php/sbcars/article/view/29033) (сниппет)

Polling:
- Опрос определяется по периодичности: промежутки между соединениями, низкая дисперсия значит регулярный сигнал; RITA читает журналы Zeek. **[мнение, практик]** — [Black Hills](https://www.blackhillsinfosec.com/detecting-malware-beacons-with-zeek-and-rita/), [RITA](https://github.com/activecm/rita)
- RITA нужен минимум соединений на пару; логнормальные промежутки трафика LLM-агентов выпадают из области её эвристик. **[независимое]** — [arXiv 2609.19091](https://arxiv.org/pdf/2609.19091) (сниппет)

### Inferences
- Метрики, которые стоит считать, потому что они вычисляются из журналов и реестра и сравниваются с собой между выпусками:

| метрика | источник | что ловит | доказательность |
|---|---|---|---|
| сообщений на действие, по видам действий | журнал, группировка по исходному действию | лишние обмены | гипотеза, связи с инцидентами нет |
| длина пути, максимум переходов | журнал, родительский кадр | лишний посредник | гипотеза; синхронная цепочка упоминается в CLOSER 2021 |
| разных вариантов пути на одно действие | журнал, варианты | второй путь | гипотеза |
| повторы одного `type` в действии | журнал | петля, chatty | эвристика блога |
| типы без отправителя или приёмника | реестр в коде | мёртвое, ошибка | проверено на аналогах: ROSDiscover 8 из 19, RADAR |
| мест реализации retry и слоёв retry на пути | реестр ролей | усиление нагрузки | сильная для retry вообще: OSDI '22 |
| период и коэффициент вариации пар | журнал | polling | метод из безопасности, для этой цели не проверен |
| циклы в графе модулей | код, манифесты | цикл | обычная практика, надёжно считается |

- Из всех дубликатов механизмов сильнее всего оправдан счёт retry: только здесь есть данные по реальным инцидентам. Но OSDI '22 говорит о retry вообще, а не о двух retry подряд; вывод о слоях — это арифметика.
- Абсолютные пороги брать неоткуда: данные Meta и Alibaba относятся к другому масштабу и описывают форму, а не качество. Измеримое изменение числа между сборками полезнее любого порога.
- Вывод Schnoor и Hasselbring подсказывает считать оба графа: статический показывает, что есть, динамический — что работает. Различие между ними и есть находка.
- Польза для малой команды убывает в таком порядке: реестр типов кадров, реестр ролей, сообщения на действие из журнала тестового прогона, варианты пути, период polling, process mining как инструмент. Первые два работают без трафика; третий и четвёртый — на журналах тестового флота при наличии идентификатора исходного действия.

### Gaps
- Не найдено опубликованных данных, связывающих число переходов, fan-out или сообщений на пользовательское действие с инцидентами, дефектами или стоимостью сопровождения в микросервисах.
- Утверждение о значимом отрицательном влиянии Cyclic Dependency и Shared Persistence на производительность встретилось только в поисковой выдержке без проверяемого источника, поэтому в выводы не включено.
- Не найдено исследований, измеряющих вред двух независимых механизмов одной роли рядом (двух очередей, двух журналов, двух retry).
- Не найдено работ о polling как архитектурном запахе и его обнаружении по журналам в микросервисах; метод взят из обнаружения маяков в безопасности.
- Исходная статья «The Tail at Scale» не читалась; цифра подтверждается арифметикой.
