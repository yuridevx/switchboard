## Вопросы брифа

- **Часть, снятая остановкой ОС, не поднимается следующим планом.** Достижимо и вредит, поправлено (потеря 2). rev один на весь флот (`workers/releases/src/fleet.ts`), поэтому новый план доходит при любой смене флота и подключении; старый код на нём часть поднимал. Сигнал держателю при живом keeper: Linux — `kill` держателя (тест). Windows — вывод из документации HandlerRoutine, не опыт: `CTRL_LOGOFF_EVENT` система шлёт консольным процессам при выходе любого пользователя, получают его только службы, служба при этом работает дальше. Доходит ли он до держателя, потомка службы, живьём не проверено. Довод первого прохода «остановка ОС кончается перезапуском keeper» этот случай не покрывает. Тот же корень без ОС: «убей» по force, план заменён следующим с on:true, пока цикл занят, — воспроизведено на обеих ОС, поэтому правка не зависит от проверки на Windows.
- **`/Run` после `/Create` в `install --logon`.** Снято, без правки. Документация: `RegistrationTrigger` запускает задачу, когда она зарегистрирована или обновлена, `/Run` его дублирует; старый комментарий подтверждает живым прогоном 1 нояб.: повтор идёт «с установки». Цена, если триггер не сработает: keeper не поднимется до входа. Задачи ставить запрещено, поэтому своим опытом не проверено.

## Отличается без вреда: запись

| группа | старое → новое | почему без вреда |
|---|---|---|
| копия журнала в stderr консоли (`echo`) | `keeper run` печатал строки → молчит | те же строки в файле журнала; потребителей нет (`journalctl` в репо нет) |
| порядок полей журнала | t, part, machine… → по алфавиту | читатели разбирают JSON (journal.ts) |
| поля и имена строк | `ev: stderr` → `ev: out, stream: stderr`; `install` → `part_failed`; `adopt`, `orphan_kill` под именем части; нет `id` у строк сессий, `version` у `part_failed`, `bytes`, `stderr` у `held_exit` | журнал фильтрует по `part`, `kind`, `callsign`; страница показывает `ev, word, why` (tabs.tsx:200) |
| пауза после принятого hello | 1, 1, 2 → 1, 2, 4 | первая пауза та же, разница — один шаг (link.go:54) |
| причина закрытия | `keeper stop` → `keeper_stop` | relay только печатает; поиск по репо пуст |
| пользователь задачи | токен → `USERDOMAIN\USERNAME` (service_windows.go:161) | переменные есть в консоли и ssh; пустых опытом не воспроизвести без установки задачи. Служба берёт токен: два способа в одном файле |
| `hideConsole` | `ShowWindow` → `FreeConsole` | документация HandlerRoutine: `CTRL_LOGOFF_EVENT` и `CTRL_SHUTDOWN_EVENT` получают только службы, интерактивные приложения к этому мигу сняты, то есть задача при входе не получала их и со старым кодом; жёсткий выход — ожидаемая ветка. Живьём не проверено |
| перезапуск после падения | версия плана → версия процесса (`p.run`) | версия, которая не встала, не роняет работавшую |

| `orphan` | предел 5 с → `Stop` | остановка прерывает ожидание |
