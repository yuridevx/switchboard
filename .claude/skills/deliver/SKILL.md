# Делай

Принятое становится работающим на флоте, и это доказано числами. Ведёт главная сессия в персоне архитектора. Устав и персона уже в контексте — здесь только порядок, команды и ловушки, которых в них нет.

Проверяет и выкладывает CI. Сессия пишет код и одну свою проверку; на флот с компьютера сессии ничего не идёт.

```
код + своя проверка → push, PR → проверка CI: части и коробка → main → выкладка на тестовый флот → fleet/test → окружение → «в прод» → fleet/prod
```

## Готово, когда

- каждая строка «Готово» доказана прогоном CI: число до и после, ссылка на прогон;
- открытых находок 0;
- второй проход сделан: хвосты, меняющие поведение, доделаны; дубликатов, лишних коммуникаций и циклов 0;
- итог сдан.

## Вход

Работа начинается со строк «Готово»: без них нечем доказать конец. Строка называет проверку — эталон или живой шаг — и число.

| запрос | откуда строки «Готово» |
|---|---|
| «делай» по дизайну | блок «Порядок реализации» принятого дизайна |
| «делай» по плану из разговора | пишешь сам по плану |
| «поправь», «поработай над» | сначала диагностика — факты из журнала, причина, слой и нарушенный инвариант; потом строки по ней |

План правки, которого не было в принятом дизайне, проходит гейт персоны до первой строки кода: дубликат дешевле не написать, чем сводить.

Число «до» — из итога последнего прогона main: `gh run list --branch main --limit 3`, сводка на странице прогона. У себя его не снимают.

## Код

Порядок — по зависимостям, от стабильного: protocol → Worker-модули → ядро Host → модули Host → web → keeper.

У себя сессия запускает одну свою проверку — ту, что пишет сейчас:

| своя проверка | команда |
|---|---|
| файл теста | `npx vitest run <файл>` в папке пакета |
| снимок тронутого экрана | страница на моке: `npx vite --port <порт> --strictPort` в `web/`, адрес с `?mock`; сценарий — свой `shots.mjs` |
| свой живой шаг | в коробке, через список по названию строки: `SB2_ONLY="смена модели" node tools/box/box.mjs node tools/fleet/live.mjs box cli m1 m2`; часть длинной проверки — своя строка списка, `SB2_PART` стоит в её окружении |
| живой шаг, которому нужно окружение | на тестовом флоте, после того как CI выложил main, — той же командой без коробки: `SB2_ONLY="…" node tools/fleet/live.mjs test cli <машина> <вторая>`; строке с местом `руками` — ещё `SB2_ALL=1` |

Коробка — весь Switchboard на своём компьютере: платформа и службы, страница, две машины с Host и claude, поддельная модель; ни флота, ни ключей ей не нужно. `node tools/box/box.mjs` без команды держит её поднятой и печатает адрес страницы со входом. История флота идёт в коробке, когда ей дан настоящий ClickHouse: `docker run -d --rm -p 127.0.0.1:18123:8123 -e CLICKHOUSE_PASSWORD=box clickhouse/clickhouse-server` и `SB2_BOX_CH=http://default:box@127.0.0.1:18123` перед командой; без адреса шаги с историей не идут. На раннере его поднимает сама работа.

Правило импортов, типы, пакет целиком, все тесты и живой список целиком сессия не гоняет: это делает CI на каждый push. Пакет целиком, когда без него не разобраться, — `node tools/test/run.mjs <часть>`.

## Выпуск

Коммит, push и слияние входят в «делай» — отдельного слова не ждут.

1. Коммит своих путей → push → `gh pr create` → `gh pr merge --auto --merge`. Зелёный PR сливается сам; красный main не принимает. Автослияние GitHub срабатывает через 5–120 с после зелёной проверки; чтобы не ждать, фоном: `gh pr checks <номер> --watch --interval 5 && gh pr merge <номер> --merge`.
2. Красная проверка: `gh run view <номер> --log-failed` → правка → push.
3. Слияние запускает выкладку на тестовый флот (`deploy`): выкладывается только изменившееся — по отпечатку кода, в порядке платформа → службы со страницей → машины. Прошедшая выкладка двигает ветку-метку `fleet/test`: код проверен до слияния, от окружения теста метка не зависит.
4. После метки тот же прогон гонит на самом тестовом флоте швы — шаг «окружение»: строки списка с местом `флот`, чьё свойство требует настоящей службы (модель, аккаунты, хранилище, уведомления). Красный шов — находка о стыке с настоящей службой или об окружении: читаешь, чья она. Стык — правка следующим PR; окружение (занятая машина, предел ключа) — строка в итог. Весь список на флоте — ручным запуском перед «в прод» (раздел «Прод»).
5. Плавающее: после слияния `node tools/test/history.mjs` печатает по местам работы и шаги, красные из них, ворота слияния и плавающие шаги — один код, одно место, два исхода. Плавающий шаг — баг проверки или гонка в продукте: сразу в бэклог (правило устава о багах).

Пока идёт CI — второй проход, не ожидание.

Что где стоит:

```
git fetch origin
git log --oneline origin/fleet/test..origin/main         # слито, ещё проверяется
git log --oneline origin/fleet/prod..origin/fleet/test   # уйдёт в прод
node tools/deploy/fleet.mjs test cli --plan              # какие части отличаются от того, что на флоте
```

Как писать живую проверку — обвязка `tools/fleet/harness.mjs`, образцы `live-switch.mjs`, `live-page.mjs`, `live-rewind.ts`. У проверки три входа: код, свой зафиксированный вход и сигналы системы; время, соседи и внешний мир входом не бывают.

- Проверка — `await check(async (t) => { … })`, шаги — `t.step("суть", …)`; длинная делится на части — `t.only("<часть>")` и строка списка на часть.
- Ждёшь только сигнал или факт: `t.wait("что", read)`, итог хода — `s.turn`, `s.ended`, `s.after`, ожидания страницы — без своих чисел. Пауз и своих пределов нет: предел один — бюджет (`BUDGET_MS`); вышел — красный шаг с «ждал» и «видел».
- Строку сессии не читаешь один раз — ждёшь значение: `t.wait("…", async () => (await s.row())?.state === "idle")`.
- «Посреди хода» держит сама проверка: `s.hold()` — ход стоит на шаге сценария до `release()`; фоновую команду или чужой ход — ворота `t.gate`.
- Сессии, папки и страницы выдаёт и убирает обвязка (`t.session`, `t.own`, `t.tmp`, `t.page`); общее, которое заводишь сам (проект, аккаунт, устройство), возвращаешь через `t.defer`. `KEEP=1` — оставить своё для разбора.
- Запрос, который трясёт общее (`SHAKES` в обвязке), проходит только по дорожке строки: флот — «одна», машину — «шумная»; иначе отказ словом до отправки.
- Первый красный шаг останавливает проверку; исхода «ждёт выкладки» нет.
- Новая проверка — строка `tools/fleet/list.mjs` с полем «где идёт»: `коробка` — свойство потока между частями, держит слияние; `флот` — шов, свойству нужна настоящая служба; `прод` — годна проду; `руками` — на флоте только во всём списке. Без строки её никто не запустит.
- Таймер, сон и своё число `timeout` в проверку не пустит правило сборки (`tools/gate/gate.mjs`, шестое).

Ловушки:

- Просьба к модели в живой проверке — сценарий хода (`tools/fleet/turn.mjs`): шаги «вызови инструмент с полями» и «ответь текстом». Просьбу словами поддельная модель коробки не исполнит.
- Шагу нужно то, чего в коробке нет (уведомления браузера, понимание модели), — он называет это: `t.lacks("r2")` у шага или седьмое поле строки списка. Имена — в `tools/fleet/harness.mjs`.
- Claude в коробке играет двойник модели: два аккаунта с его адресом в поле `base`. Отказ ему заказывает сам токен аккаунта: `…not-a-token` — 401, `…full-after-N` — лимит недели, когда в разговоре уже N ответов модели. Шаг с заказом идёт, только когда адрес аккаунта — этот компьютер: настоящему аккаунту токен не меняют.
- Машины коробки ставит и держит служба машины из сборки; сборку в каталог флота несёт шаг «машины» выкладки (`tools/deploy/machines.mjs`) — он же у CI и у проверки «выкладка сборки». Эта проверка идёт только в коробке (`local()`): на живой флот сборку доводит CI.
- Время пути: проверка PR — около 2,5 мин (коробка), выкладка до метки — около минуты, швы на флоте — ещё около 3 мин. Стало заметно дольше — это находка.
- Живой список ходит только на ключи, названные в переменных репо (`SB2_KEY`, `SB2_SWITCH`). Чужой ключ с пределом трат (на тестовом флоте — `deepseek`) в список не входит: проверка на нём — запуском файла мимо списка, `SB2_PART=provider node tools/fleet/live-accounts.ts test cli <машина>`, модель — бесплатная из каталога (`…-free`).
- Красная коробка печатает после списка хвосты журналов своих частей: платформа, службы, Host каждой машины и модель — что у неё спросили и что она ответила.
- На тесте всегда main: правка живого поведения идёт слиянием, а не выкладкой ветки.
- Основное дерево общее с другими сессиями — работаешь в своём worktree; `npm ci` — в нём же.
- Сломан инструмент выкладки или живая проверка — правка тем же путём, через PR.

`test-cycle` — по слову пользователя или когда меняется поток между частями.

## Прод

Только по слову пользователя: `gh workflow run deploy.yml -f fleet=prod`. Перед запуском — весь список на тестовом флоте: `gh workflow run deploy.yml -f fleet=test -f list=весь`; красный по вине кода закрывается до прода. На прод идёт ровно коммит `fleet/test`; зелёная проверка прода двигает `fleet/prod`. Сессии до и после и номера отката — в итоге прогона.

Закрыт, когда прогон зелёный и `git log origin/fleet/prod..origin/fleet/test` пуст.

## Слепой архитектор

Только по слову пользователя («слепой архитектор», «пройдись архитектором» по диффу): новый агент `architect` на дифф — коммиты или пути и охват. Код правишь по его отчёту ты; находок гейта после — 0.

## Второй проход

Один: принятое и гейт персоны против результата. Что делать с хвостами — правило устава. Хвост идёт тем же путём: push, проверка, тестовый флот.

## По ходу

- Смена шага — одна строка пользователю: что сделано, что дальше.
- Шаг пропущен — одна строка с причиной сразу, не в итоге.
- Факт противоречит принятому — решение пользователя не меняешь: делаешь закрывающий вариант, развилка идёт в итог.

`<scratchpad>/deliver/<slug>/plan.md` — рабочая память на случай сжатия контекста: строки «Готово» с числами до и после и статусом, отложенные половины, решения развилок одной строкой.

## Итог

- **Готово:** строка → проверка → число до и после → ссылка на прогон.
- **Гейт:** дубликаты, лишние коммуникации и циклы до и после второго прохода; слепой архитектор, если был, — находок до и после.
- **Выпуск:** прогон выкладки, что выложено; коробка и список окружения числами; итог test-cycle, если был.
- **Развилки:** решённые — одной строкой; задевшие решение пользователя — с закрывающим вариантом, который сделан.
