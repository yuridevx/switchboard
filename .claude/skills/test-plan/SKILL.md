# План тестов

Цель: для охвата X — модуля, Worker-модуля, приложения, всего репо или названных флоу, как назвал пользователь или deliver, — план флоу, по которому пишутся тесты и прогоняется система.

## Что на выходе

`<scratchpad>/test-plan/<slug>/` (`slug` — kebab-имя охвата):

- `flows/<flow-id>.md` — страница на флоу;
- `plan.md` — итог: охват, карта покрытия, нерешённое.

## Понятия

| понятие | что это |
|---|---|
| вход | место в коде, где начинается флоу по внешнему стимулу: кадр, запрос, HTTP или WebSocket Worker-модуля, событие SDK, сигнал ОС, таймер, действие в веб-приложении, команда CLI |
| флоу | путь от одного входа до наблюдаемого исхода; у флоу одна часть-владелец |
| сквозной флоу | флоу через две и больше частей по их контрактам; инициатор один |
| наблюдаемый исход | видно снаружи части: ответ `reply`, кадр, поле roster, запись в хранилище, строка журнала с причиной, процесс поднят или остановлен, сообщение во вводе сессии, экран, пуш — или документированное отсутствие этого |
| ветка | развилка в коде, которая даёт другой наблюдаемый исход |
| `flow-id` | стабильное kebab-имя из стимула и символа входа: `request-session-prompt`, `frame-message`, `timer-points-retention`, `cross-fleet-send`; тот же код — то же имя |

## Какие сценарии

- **HAPPY** — основной путь флоу.
- **NEGATIVE** — только ожидаемые ветки устава: закрытый список восстановления, отказ «система ловит» (остановила, отказала, записала причину) и штатная остановка, если она у части есть. Один «вход отклонён» покрывает всю валидацию входа.
- Сценарий начинается на входе и кончается наблюдаемым исходом. Внутреннее состояние части не проверяется. «Ожидаем» — только то, расхождение с чем было бы находкой (определение — fix-findings).

## Страница флоу

```markdown
# <flow-id>

## Флоу
Стимул: <кадр / запрос / таймер / …>
Вход: <файл>:<строка>
Суть: <одна фраза>

## Сценарии

### <имя по сути> · HAPPY
- Условия: хранилище — …; вход — …; настройка — …; соседи — …
- Шаги: 1. … 2. …
- Ожидаем: <наблюдаемый исход> — источник: слово пользователя «…» | факт: … | чьё: код
- Подделки: нет | <граница> — <почему>
- Код: <файл>:<строка>, …
- Тест: <файл> · <номер> · <имя> | вживую — ставит test-cover

### <имя по сути> · NEGATIVE
- Ветка: <файл>:<строка> — <условие>
- (те же поля)
```

В сквозном флоу шаг — `часть → часть: кадр или запрос`, без внутренних шагов частей.

## Правила страницы

1. Источник истины — код и слово пользователя (устав, принятые дизайны). Существующие тесты, README и прочие документы — не доказательство: «Ожидаем» на них не ссылается.
2. У каждого «Ожидаем» есть источник.
3. Каждая ссылка `файл:строка` указывает на тот символ, о котором сказано.
4. Каждый вход охвата — ровно в одном флоу или в исключении с причиной.
5. Каждая ожидаемая ветка — сценарий NEGATIVE со строкой «Ветка».
6. Подделка — только на границе части (SDK, Relay, Keeper, часы, внешние сервисы), с названной границей и причиной. Соседние модули внутри флоу — настоящие.
7. Условия описаны словами, без ссылок на фикстуры.
8. Имена сценариев уникальны на странице и говорят суть: «повтор после смерти процесса», а не «error case».
9. Пустых разделов нет.

## Проверка страницы

Каждую страницу после автора проверяет независимый агент, который автора не видел: сверяет с кодом и правилами. Правки — только по существу: нет обязательного поля, утверждение противоречит коду, вход или ветка без сценария, неверная ссылка, нарушено правило. Редакторских правок нет: формулировки, порядок и оформление не трогаются. Проверка одна на страницу; что она не закрыла — в «нерешённое».

## plan.md

- Охват: части, входы, флоу, сквозные флоу, сценарии HAPPY и NEGATIVE — числами.
- Карта покрытия: вход → флоу или исключение; ветка → сценарий. Сирот нет.
- Нерешённое: пункт, страница, причина и закрывающий вариант — им пункт и закрыт, если пользователь не скажет иначе.

## Границы

- План только описывает: код и тесты не правит.
- Решения развилок — одной строкой в `plan.md`.

Готово, когда все страницы прошли проверку, карта покрытия без сирот и у каждого «Ожидаем» есть источник.
