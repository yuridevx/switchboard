приложение Claude SDK

Ядро Host

Host — процесс Node с Claude Agent SDK, один на машину. Только он говорит с сессиями Claude Code: на каждую сессию — один query(), а процессы claude держит keeper. Ядро не знает ни одной функции. Оно ведёт сессии, держит соединения с keeper и relay, собирает вклады модулей и следит, чтобы у каждого имени был один владелец. Всё, что видят люди и сессии, делают модули — каждый в своём пакете монорепо, со своей версией и манифестом. Новый выпуск модулей ядро ставит в живом Host — без перезапуска Host и сессий.

query() одна сессия Claude Code в SDK модуль функция Host: fleet, questions, watch… пакет папка монорепо со своей версией: модуль cost — пакет host-cost манифест module.json: что пакет даёт (provides) и чем пользуется (uses) вклад что модуль отдаёт ядру: запрос, поле, хук владелец единственный пакет у имени выпуск Host в R2: ядро, модули и SDK точных версий keeper служба ОС: держит процессы claude relay Worker в Cloudflare: roster и доставка по адресу

Вклады модулей — в их частях: fleet · questions · watch · chat · manage · slots · accounts · profiles · points · remote · machine · upgrade · push · journal. Worker-модули — relay, gate, push, points, ledger, github; каналы и ключи — экосистема.

Что проходит через ядро

Шесть случаев по шагам. Ядро находит владельца и передаёт ему; само ничего не решает.

    Одна сессия — один query()

    Ядро собирает параметры query() из своих и из вкладов модулей, отдаёт SDK очередь ввода и читает поток сообщений. Свой протокол stdin не пишется: в процесс claude пишет только SDK.

    Жизнь сессии

    Состояния, которые ядро показывает в roster, и ветки, которые оно поднимает само. Неожиданный сбой сессии — чистый перезапуск по resume; второй до готовности — failed, причина в журнале.

      Модуль — пакет монорепо

      Гейт: сборка монорепо и старт Host

      1. Один владелец у имени во всём монорепо: у запроса, кадра, поля roster — в Host, Worker-модулях и приложениях. Внутри Host — ещё у MCP-сервера, ключа env и settings, опции query(), решения по инструменту. Хуки и append владельца не имеют — складываются списком.
      2. Код равен манифесту: обработчики requests, frames, fields — ровно имена из provides; в calls — только методы query закреплённого SDK и не те, что держит ядро. Методы есть в коде SDK — входа аккаунта и Remote Control в его типах нет, это исключение устава.
      3. Каждое uses есть в provides названного владельца, той же версии v.
      4. Импорт — только вход пакета из uses. Внутренности чужого пакета — сборка падает.
      5. Старт Host: тот же гейт по списку модулей; имя Worker-модуля из uses идёт через relay — relay есть в host.json.

      Модуль работает в процессе Host

      Пакет монорепо, код — в процессе Host
      • один Node с SDK на машину: 72 МБ и +1 МБ на сессию (опыт 16)
      • вызов модуля — вызов функции; ошибку ловит ядро, модуль выключается в сессии (опыт 19)
      • хуки и canUseTool SDK зовёт внутри процесса
      • перезагрузка — новый import из папки выпуска; прежний код остаётся в памяти до перезапуска Host (опыт 21)

      Договор модуля: код

      Код модуля — объект с вкладами; что из них контракт, объявляет манифест. Ядро собирает вклады при старте, а модулю даёт свои услуги. Модули не знают друг друга: чужим пользуются только через ядро и только тем, что объявили в uses.

      что модуль отдаёт ядру 
      interface Module {
  // имя, версия, provides, uses, calls,
  // config — в манифесте пакета

  // контракт: ровно имена provides
  requests?: { [type]: (req, ctx) => Json }; // → reply
  frames?:   { [type]: (frame, ctx) => void };
  fields?:   { [name]: (s) => Json };  // поле в roster

  // вклады внутри Host — у имени один владелец
  session?:  (s) => QueryPart;         // в query()
  decide?:   { [tool]: (s, input) => PermissionResult };
  elicit?:   (s, request) => ElicitationResult;

  on?: { event?(s, msg); state?(s, state);
         frame?(f); open?(s); close?(s) };
  start?(host);              // поднять своё
  stop?();                   // снять таймеры, дописать
}
QueryPart = { mcpServers, env, append, settings, hooks,
              …опции query(): model, effort… }
ctx       = { host, from, signal }

                             // start: spawn | resume |

host.emit(frame)             // кадр без ответа: to
host.open(spec)              // новая сессия; spec.point
host.sessions()              // сессии машины: callsign, cwd, state
host.store()                 // свой раздел машины

host.log(record)             // строка в журнал машины

                             // p.sdk(имя из calls), p.close()

                             // → { code, out }

                             // → { from, to, modules, later }
host.version   host.sdk      // версия Host и его SDK
      1. s и host у каждого модуля свои. Ядро знает, кто зовёт: store() открывает только свой раздел, host.request — только имена из uses манифеста и свои, s.sdk — только имена из calls. Иначе — ошибка модуля.
      2. Имена ядра модулю не взять: у сессии callsign, state, failed, sdk; hello собирает только ядро.
      3. Модуль ставится выпуском Host — на старте Host или перезагрузкой в живом Host: порядок старта — порядок списка, остановки — обратный.
      4. s.info.start — каким был старт процесса: spawn, resume или attach. Его знает только ядро (по list keeper); модулю он нужен до старта: в файл разговора живого процесса писать нельзя. point — resume по разговору, который положили из точки: так старт отмечает тот, кто поднимает, номером точки — s.start({ point: 318 }) или host.open({ …, point: 318 }); поле point то же, что в запросах manage.
      5. host.probe и host.cli — claude без сессии. Тот же закреплённый claude, что у сессий, со своим env: вход и опрос аккаунта. Не в roster, не у keeper, умирает с Host; методы — только из calls модуля.

      Ловушка ошибок модуля

      Каждый вызов модуля ядро оборачивает. Ошибка не идёт дальше: модуль выключается в этой сессии, остальные работают. Самопочинки нет — чинит агент по журналу.

      buggy бросил ошибку→выключен в site@laptop→failed: { "host-buggy": причина } в roster→журнал: стек и сообщение SDK→агент чинит: новый выпуск → перезагрузка модуля
      requestsreply ok:false, error: module_error
      framesкадр дальше не идёт, строка в журнале
      on.*следующие модули получают сообщение как обычно
      session()query() собран без вкладов модуля
      hooksхук отвечает {} — как будто его нет; другие хуки события вызваны
      decide{ behavior: "deny", message: "module_error" } — модель идёт дальше
      elicit{ action: "decline" }
      fields · helloполе не отдаётся
      start()модуль выключен на всей машине, failed в roster каждой сессии — на старте Host и при перезагрузке одинаково; Host работает дальше
      stop()строка в журнале, остановка идёт дальше

      Вызов без сессии — запрос с machine — выключает модуль на всей машине. Выключенный модуль остаётся выключенным до перезапуска Host или перезагрузки — чинит агент новым выпуском; в других сессиях он работает (опыт 19).

      Хранилище

      Всё долгое во флоте лежит на машинах, у Host: relay на диск не пишет. У каждого раздела один владелец — модуль с тем же именем.

  host.key      ключ машины: читает только
                пользователь ОС
  store/

      1. s.store() — раздел модуля для этой сессии, host.store() — для машины. Чужие разделы не видны. s.remove() стирает разделы этой сессии у всех модулей: настройка сессии — слот, профиль, пометка «в R2» — уходит вместе с сессией, второго места у неё нет.
      2. Запись сразу: set и update пишут файл — временный и rename. Файл всегда целый JSON.

      4. Ждущие вопросы хранить не нужно: после перезапуска Host их отдаёт SDK с тем же toolUseID (опыт 20).

      Соединения: keeper и Worker-модули

      Ядро открывает соединения из списка в host.json — сейчас это один relay; имена Worker-модулей модуль объявляет в uses манифеста. Модуль сокетов не держит: всё через ядро. Связь с relay — hello, пауза переподключения, ждущие запросы по id и disconnected, когда машина адресата ушла из roster, — один клиент link из пакета relay: его же зовут ядро веб-приложений и скрипты. Правило отправителя живёт в одном коде. Устройство самих каналов — в частях relay и keeper.

      старт Host
      1. Строка keeper из stdin: порт и ключ.
      2. Гейт: код равен манифесту, один владелец, uses и версии. Не прошёл — выход с причиной.
      3. start(host) модулей по порядку списка.
      4. keeper: соединение управления, list → живые процессы.
      5. Сессии из списка: процесс жив и SDK тот же — attach; жив, SDK другой — attach и restart; процесса нет — resume; stopped — остаётся. Процесс, которого нет в списке, — kill и строка в журнале.
      6. Каждый Worker из списка: wss и hello с contract — provides модулей — и сессиями.
      7. Готов: у каждой сессии ответ initialize или failed — ready в keeper.

        Перезагрузка модуля в живом Host

        Новый выпуск, в котором другие только пакеты модулей, ядро ставит без перезапуска Host и сессий: старая версия модуля штатно останавливается, новая поднимается из того же хранилища. Процессы claude, разговоры и начатые ходы не прерываются (опыт 21). Другое ядро или SDK — новый Host через keeper; сессии и тогда живут — по attach.

          Вклады в живые сессии

          сразув живом query() со стартасо следующего старта сессии
          • код модулясразуrequests, frames, fields, on.* — ядро зовёт новую версию
          • decide · elicitсразуcanUseTool и onElicitation в query() — функции ядра: владельца ищут на каждом вызове
          • hooks · теласразув query() — обёртки ядра; зовут хук нынешней версии (опыт 21)
          • mcpServersсразуsetMcpServers — без серверов модуля, затем с новыми: сервер того же имени один вызов не заменяет. Вызов инструмента модуля, начатый до замены, обрывается: модель получает ошибку «Connection closed» и идёт дальше (опыт 21)
          • settingsсразуapplyFlagSettings — разница ключей модуля; снятый ключ — null
          • model · effortсразуsetModel, applyFlagSettings({ effortLevel })
          • hooks · новое событиесо стартанабор событий и matcher SDK отдаёт claude один раз — в initialize (код SDK 0.3.311, опыт 21)
          • appendсо стартачасть initialize; метода нет
          • envсо стартаокружение процесса claude

          «Со старта» — со следующего старта процесса сессии: resume после сбоя, session.start, новая версия SDK. Ради этого ядро сессию не перезапускает: такие сессии — в ответе later и строкой в журнале. Новая версия модуля работает и с прежними env и append до этого старта. Методы — по типам SDK 0.3.311: setMcpServers, applyFlagSettings, setModel есть у query; у append, env и набора хуков метода нет.

          Правила перезагрузки

          1. Единица — выпуск. Модуль приходит выпуском Host из R2, а не сам по себе: гейт проверяет список выпуска целиком. Пакеты, чьи uses поменялись вместе, перезагружаются вместе — старт по порядку списка, остановка в обратном.
          2. Перезагрузить или перезапустить — решает ядро: ядро и SDK в выпуске те же — перезагрузка; другие — core_changed, и upgrade идёт к keeper. Зовёт host.reload только upgrade.
          3. Окно: вызовы модуля — запросы, кадры, сообщения SDK, хуки, decide — ждут в ядре и идут новой версии по порядку, как вывод процесса ждёт у keeper, пока Host перезапускается. Сообщения хода модуль не теряет. Начатые decide и elicit старой версии — те, что ждут человека, — ядро отдаёт новой заново с тем же toolUseID, как SDK после перезапуска Host (опыт 20).
          4. Новой версии сессии видны как после перезапуска Host: start(host), затем on.open(s) у каждой живой сессии с s.info.start — attach. Отдельного события «перезагрузка» нет.
          5. provides другие — новый hello, как на старте: в roster новый contract, ждущие ответа этой машины запросы — disconnected. Те же — соединение с relay не трогается.
          6. Без отката. start() новой версии бросил — модуль выключен на машине, failed в roster, причина в журнале; прежняя версия не поднимается. keeper не получил ready — перезапуск Host поднимет прежний выпуск.
          7. Выключенный модуль после перезагрузки снова работает во всех сессиях: новая версия стартует начисто.
          8. Старый код остаётся в памяти до перезапуска Host: модуль ES в Node не выгружается. Ядро работает из папки, с которой стартовало, — её не убирают, пока Host жив.

          Новый модуль за четыре шага

          Пример — расход сессий: поле в roster и запрос. Ядро, relay и пульт не меняются: relay пересылает запрос по callsign, поле едет в roster как есть, а пульт видит в contract машины, что запрос есть.

          // host/modules/cost/module.json
{ "name": "host-cost", "type": "sdk",
  "version": "1.0.0",
  "provides": { "session.cost": 1, "cost": 1 },
  "uses": {}, "calls": [], "config": {} }

// host/modules/cost/contract.ts
export default {
  fields: {
    cost: (s) => s.store().get() ?? { usd: 0, turns: 0 },
  },
  on: {
    event(s, m) {
      if (m.type !== "result") return;
      s.store().update((c = { usd: 0, turns: 0 }) => ({
        usd: c.usd + m.total_cost_usd,
        turns: c.turns + 1 }));
    },
  },
  requests: {
    "session.cost": (req, { host }) =>
      host.session(req.callsign).store().get(),
  },
} satisfies Module;
          1. Пакет host/modules/cost: module.json, contract.ts, код и тест.
          2. Строка в списке модулей Host и версия пакета в его зависимостях — место в порядке старта.
          3. Эталоны на стенде: поддельный SDK шлёт result — в session.state появилось поле cost, session.cost отвечает тем же; гейт монорепо: код равен манифесту, у session.cost и поля cost один владелец.
          4. Новый выпуск Host с host-cost 1.0.0 — в R2. Ядро и SDK те же, поэтому ядро ставит его перезагрузкой: cost стартует в живом Host, в hello появляется session.cost; ни Host, ни сессии не перезапускаются.

          Такой модуль прогнан в опыте 19: поле cost { usd: 0,012, turns: 1 } в roster и тот же ответ на session.cost.
