Worker-модуль

push

Веб-пуши телефону и пульту, когда приложение закрыто. Worker без адреса в интернете и участник рации с адресом push: кадры получает от relay по привязке, отвечает через relay. Три запроса — push.key, push.subscribe и push.send. Подписки клиентов хранит сам — в SQLite своего объекта, как points и ledger. Тело шифрует ключами подписки (так требует протокол веб-пушей), запрос подписывает ключом VAPID — этот ключ есть только у push.

подписка адрес службы пушей и ключи браузера клиента; хранит push клиент телефон или пульт: имя ключа, например phone notify заголовок, текст и кнопки уведомления VAPID подпись push для служб пушей; открытую половину push отдаёт по push.key служба пушей Apple, Google, Mozilla — доставляет на устройство

Не делаетне решает, когда слать пушне знает roster и соединенийне читает кадр, кроме push и subне повторяет

API push

Три запроса рации и вход участника. Запрос — обычный кадр с to: "push"; ответ — reply через relay. Выберите запрос и исход.

запрос 

        ответ
        

        

        

      

    

    
to · type · from верхнего уровня — конверт кадра для relay. Поля самого пуша вложены в push: to — имя клиента, type и from — исходного кадра, notify — что показать.

Каналы push

    
Два канала с relay по привязкам и один наружу — к службе пушей. Из интернета до push не достучаться. Нажмите номер.

  

  

    
    

  







  

    
Пуш, когда телефон закрыт

    
Решает модуль push на Host: адресата-клиента нет в roster, у кадра есть notify. push находит подписку клиента у себя и исполняет. Выберите, что ответит служба.

  

  

    
    

      что ушло в службу
      
POST https://web.push.apple.com/QK2s…
Authorization: vapid t=<JWT ES256>, k=<открытый ключ VAPID>
Content-Encoding: aes128gcm
TTL: 86400

<86 Б заголовка><шифротекст type, from, notify><16 Б тега>

      
    
        
  • Шифрование — aes128gcm ключами p256dh и auth из подписки (RFC 8291): служба видит только шифротекст.
    • 
        
  • Подпись — JWT ES256 ключом VAPID_PRIVATE (RFC 8292): aud — адрес службы, срок не больше суток.
    • 
        
  • Внутри — type, from и notify из поля push. Показывает уведомление служебный обработчик приложения — телефона или пульта; кнопка открывает приложение или шлёт ответ по короткому wss.
    • 
        
  • Ответ — reply через relay, to = from запроса. gone — подписки нет; пуши этому клиенту — после новой подписки.
    • 
      

    

  







  

    
Как клиент подписывается

    
Телефон или пульт берёт у push открытый ключ VAPID, подписывается в браузере и отдаёт подписку push. push кладёт её строкой в SQLite своего объекта. Машины о подписках не знают: любая из них шлёт push.send с именем клиента.

  

  

    
    

      SQLite объекта push · одна строка на клиента
      
client      endpoint                         p256dh  auth  at
phone       https://web.push.apple.com/QK2…  BN…     k3…   1730297400000
panel-desk  https://fcm.googleapis.com/fcm…  BC…     q9…   1730301000000

      
    
        
  • client — из from запроса. Чужую подписку не записать и не стереть.
    • 
        
  • Одна строка на клиента: новый push.subscribe заменяет прежнюю. 404 или 410 от службы — строка удалена.
    • 
        
  • Ключ VAPID — один секрет VAPID_PRIVATE (JWK); открытую половину push выводит из него и отдаёт по push.key. Смена ключа — выпуск только push, приложения подписываются заново.
    • 
        
  • Объект — один на флот, idFromName("home"), как у points и ledger. Выпуск и перезапуск строк не теряют.
    •

Сбои и остановка

    
Подписки лежат в SQLite объекта push: выпуск и перезапуск их не теряют, строка пишется сразу. Остановкой управляет Cloudflare; для отправителя это offline на один запрос. Повторов push не делает — повторить решает отправитель.

Эталоны push

    
Каждый проверяет push на зафиксированном входе: служба пушей поддельная, SQLite объекта — чистый, ключи подписки и VAPID заданы в тесте. Номер эталона — номер теста.

  

  

    
5

      
У push есть подписка phone. Модуль push на Host laptop шлёт push.send с push { to: "phone", type: "question", from: "profiles@laptop", notify } — заголовок, текст, варианты. Служба отвечает 201.

      
Служба получила один POST на адрес подписки phone; расшифрованный ключами телефона — type, from и notify с заголовком, текстом и вариантами. Host laptop получил reply ok, result: { cut: false }. Кроме push, push в кадре ничего не читал; строка phone в SQLite не изменилась.

      
чьё: устав — «достают до телефона»; слово пользователя 31 окт. — разложение relay → relay, gate, push («подтверждаю разложение, не детали»).

    
42

      
Телефон сделал push.subscribe и закрылся. Выпущены relay и push; затем Host laptop шлёт push.send для phone с notify вопроса.

      
Пуш ушёл по подписке, записанной до выпусков; телефон не переподключался; relay подписку не хранил; Host подписку не присылал.

      
чьё: устав — «Relay не пишет на диск», «достают до телефона»; факт — SQLite Durable Object переживает выпуск Worker (Cloudflare).

    
43

      
push.send с id: "s-9" для phone; служба отвечает 410. Следом — ещё один push.send для phone.

      
Первый — reply { id: "s-9", ok: false, error: "gone" }, строки phone в SQLite нет, в журнале push — 410 и адрес службы; повторного POST нет. Второй — gone без POST.

      
чьё: факт — протокол веб-пушей (RFC 8030): 404 и 410 — подписки больше нет; устав — «Система ловит, агент чинит».

    
48

      
push.send с id: "s-5", notify.body — 6 000 байт; служба отвечает 201.

      
В уведомлении — начало текста; тело POST не больше 4 096 байт; reply { id: "s-5", ok: true, result: { cut: true } }.

      
чьё: факт — службы пушей обязаны принимать тело до 4 096 байт (RFC 8030); открытого текста в нём — до 3 993 байт (RFC 8291).

    
120

      
Телефон шлёт push.subscribe с подпиской; relay поставил from: "phone". Затем Host шлёт push.send с push.to: "phone". Потом phone присылает подписку с другим адресом, а panel-desk — свою.

      
На подписку — reply ok; пуш ушёл на адрес из неё. После второй подписки в SQLite одна строка phone — с новым адресом; строка panel-desk своя, строку phone она не тронула.

      
чьё: устав — «Части независимы и пользуются друг другом только через контракт»; отправителя ставит relay.

    
121

      
push.send с id: "s-6"; служба отвечает 503.

      
reply { id: "s-6", ok: false, error: "push_failed" }; в журнале push — 503 и адрес службы; повторного POST нет; строка подписки на месте.

      
чьё: устав — «Система ловит, агент чинит»: код только обнаруживает ошибку, пишет в журнал с причиной.

    
122

      
relay зовёт hello() у push.

      
{ contract: { "push.key": 1, "push.send": 1, "push.subscribe": 1 } } — ровно те запросы, что push обслуживает.

      
чьё: слово пользователя 31 окт. — «они тоже должны быть модульными»; устав — «Части независимы и пользуются друг другом только через контракт».

    
123

      
push.send на поддельную службу https://push.example/….

      
У POST: Content-Encoding: aes128gcm, заголовок TTL, Authorization: vapid t=…, k=…; JWT проверяется открытым ключом VAPID, aud = https://push.example, срок не больше суток; тело расшифровывается ключами подписки.

      
чьё: факт — RFC 8291 (шифрование), RFC 8292 (VAPID), RFC 8030 (заголовок TTL обязателен).

    
124

      
VAPID_PRIVATE теста — JWK; телефон шлёт push.key.

      
reply ok, result: { key } — несжатая точка P-256 (65 байт) в base64url, та же, что x и y JWK; подпись JWT из эталона 123 проверяется этим ключом. Настройки VAPID_PUBLIC у push нет.

      
чьё: факт — RFC 8292: открытый ключ сервера приложения — несжатая точка P-256 в base64url.
