Switchboard

Независимая экосистема модулей четырёх типов: Worker в Cloudflare, приложение для ОС, приложение Claude SDK и веб-приложение. Модуль — пакет со своим манифестом; наружу он отдаёт только контракт, и говорят модули друг с другом тремя способами — других нет. Первый набор модулей — рация для сессий Claude Code: сессии на разных машинах и в разных аккаунтах видят друг друга, переписываются по позывным и достают до телефона владельца.

callsign позывной сессии: site@laptop machine laptop — адрес машины: @laptop fleet home — все машины и клиенты владельца slot main — папка входа аккаунта Claude attachment карточка соединения в relay module пакет: relay, gate, host-fleet, web-ask… provides имена контракта модуля и их версии участник у кого есть адрес в рации

Рация — набор модулей

Функция рации — это не одна программа, а несколько модулей разных типов, которые пользуются друг другом через контракты. Выберите функцию — подсветятся её модули и связи. Нажмите модуль — что он такое и где его часть.

Модуль — одна модель на четыре типа

Модуль — это папка, она же пакет монорепо: npm workspaces для TypeScript, Go-модуль для приложений ОС. В папке — манифест module.json: имя, тип, версия, что модуль отдаёт, чем пользуется и какие ключи ему нужны. Наружу пакет отдаёт только контракт.

    Флот в работе
    
    
    Выберите случай и пройдите по шагам. На каждом шаге — каким способом и по какому каналу идёт кадр и какой ключ его пропускает. Цифра на линии — способ связи: 1 — кадр через relay, 3 — привязка, 4 — локальный канал; ↗ — наружу. Случаи с пометкой «опыт» прогнаны на настоящем Claude Code и Agent SDK.
    
  
    
  
    
    
    
    
    
      
    
      
    
        
    
        
    
      
    
    
    
    
    
      
      
      
      
    
    
    
      
  
      

      



      
  
      
    
      Доверие и ключи
      
    
      Флот — одна зона доверия: держатель любого ключа и любая сессия могут дать любой сессии любую задачу. Поэтому граница одна — ключ, а защита — свой ключ у каждого устройства и его отзыв. Секрет лежит только у модуля, которому он нужен. Worker без публичного адреса достижим только по привязке, и привязка в конфиге — это и есть доверие.
      
  
      
  
      
    

    
      
      
      
        
      Ключ — имя, подписанное секретом флота
      
        
      
          hostроль.
          laptopимя.
          k7f3номер.
          Jx9…подпись
        
      
        
        
          
      1. Проверка без списка. gate считает HMAC-SHA256 от host.laptop.k7f3 секретом FLEET_SECRET и сравнивает с подписью. relay секрета не видит: зовёт gate.verify и получает роль и имя. Списка выданных ключей нет нигде.
        2. 
          
      2. Роль решает, кем соединение может встать: host — машиной со своими callsign, client — клиентом.
        3. 
          
      3. Номер — короткий случайный. Отзывают номер, а не имя: машина получает новый ключ, её callsign не меняются.
        4. 
          
      4. Выдача — switchboard invite, инструмент из пакета gate: секрет флота читает из stdin, ключ печатает в stdout для следующей команды. В аргументах команды секретов нет.
        5. 
        
      
      
      
      
      
        
      Отзыв — выпуск gate, затем relay
      
        
        
          
      1. Номер ключа — в список REVOKED в настройках gate; список не секрет и лежит рядом с кодом gate
        2.

      Контракт модуля
      
    
      Модуль пользуется другим только через контракт владельца: имя кадра или метода, его поля, версию и слова ошибок. Чужой код не импортирует, чужих полей не трогает. Общий у всех — только конверт кадра.
      
  
      
  
      
    
      
      
      Конверт кадра — пакет protocol, без имён модулей
      
      
      { "type": "session.history", // один владелец
  "id": "h-3",               // запрос: ждёт reply
  "v": 1,                    // версия имени
  "callsign": "site@laptop", // куда: Host машины
  "from": "panel-desk",      // ставит relay
  "before": "…" }            // поля владельца

{ "type": "push.send", "id": "p-4", "v": 1,
  "to": "push", … }          // Worker-модуль

{ "type": "reply", "id": "h-3",
  "ok": true, "result": { … } }
{ "type": "reply", "id": "h-3",
  "ok": false, "error": "contract_mismatch" }
      
      
        
        
      1. Куда везти. callsign или machine — Host этой машины, как есть. to — по адресу: сессия site@laptop, машина @laptop, клиент phone, Worker-модуль push. Ни того ни другого — кадр самого relay.
        2. 
        
      2. Ошибка — слово в error; подробность — строкой в журнале того, кто отказал.
        3. 
        
      3. Незнакомое поле получатель пропускает; незнакомый type — отказ.
        4. 
        
      4. protocol знает только конверт: type, id, reply, v, адрес и from. Имена кадров — у модулей-владельцев.

      Версии контрактов
      
    
      
      
      
        
        
      1. Число у каждого имени контракта: в provides манифеста, в hello и в roster; v — у запроса. proto в hello — версия контракта relay, в первой строке keeper — версия keeper.

        3. 
        
      3. Новое поле или новый запрос — та же версия. Убрать, переименовать или сменить смысл — версия +1.
        4. 
        
      4. Получатель знает свой список версий — обычно одну. Вне списка — contract_mismatch, обе версии в журнале. Переходников и выбора «ближайшей» нет.
        5.
