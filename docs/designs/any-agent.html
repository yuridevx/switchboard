Любой агент во флоте

Стандарт управления агентом называется ACP — Agent Client Protocol: одна программа (клиент) запускает агента, даёт ему задачу и получает поток его работы. По нему уже работают Claude, Codex, Gemini CLI, Copilot CLI и ещё около 60 агентов. Рекомендация: Host флота становится клиентом ACP, а агентом сессии может быть любая программа, которая говорит по ACP. Свои мосты не пишем: Claude и Codex подключаются через открытые адаптеры, остальные умеют ACP сами. Лента и чат страницы рисуются по видам событий ACP, одинаково для любого агента. Первыми после Claude — Kimi и Muse Spark (слово пользователя 3 нояб.). Один компьютер может входить в два флота сразу: у каждой системы своя служба и своя папка данных.

Четыре открытых протокола — у каждого своя пара

Управление агентом — только ACP. Остальные три решают другие задачи, и мы ими уже пользуемся или не нуждаемся.

    Новая архитектура: Host — клиент ACP

    Меняется одна граница — между Host и процессом сессии. Флот вокруг тот же: телефон и пульт идут через relay, держатель хранит процесс сессии и переживает перезапуск Host. Выберите агента — схема покажет его путь.

    агенткоманда в списке сборкисвоё в окружении процесса

    Один процесс на сессию — как сейчас: свой держатель, своё окружение, падает один. Держатель передаёт байты и не знает протокола — менять его не нужно.

    Жизнь сессии по ACP

    Состояние сессии Host знает сам, из своих же запросов: ждёт ответа на задачу — «работает», ждёт ответа человека — «ждёт вас», иначе — «свободна». Ход, который агент начал сам (Claude — по концу фоновой задачи), в ACP 1 конца не имеет: его события идут в ленту, состояние остаётся «свободна», задача в этот момент встаёт к агенту в очередь.

  • Перезапуск HostПроцесс агента живёт у держателя, его вывод копится там же. Новый Host продолжает по записи сессии — схема ниже.
  • Остановка сессииsession/cancel → конец хода → закрыть ввод процесса → процесс выходит. Не успел за лимит — держатель убивает дерево процесса.
  • Модель, усилие, режимСтандартные настройки сессии ACP: session/set_config_option. Список моделей приходит от агента, Host его не знает.
  • Своё у агентаЧто есть только у одного агента, идёт его расширением ACP: у Claude — _meta.claudeCode.options (добавка к промпту, настройки, плагины), _claude/rateLimit в потоке.

    • Перезапуск Host посреди хода и с ждущим вопросом

    Почему запись, а не новое подключение: SDK ACP нумерует запросы соединения с 0 — новый Host получил бы ответ на чужой запрос; адаптер для себя соединения не терял и свой вопрос второй раз не пришлёт. Сейчас тот же вопрос после перезапуска Host повторяет SDK (тот же toolUseID) — ядро берёт эту роль на себя. Соединение с агентом ведёт ядро: строки JSON-RPC, типы — из SDK ACP.

    История разговора — у агента

    Разговор хранит сам агент в своём файле. Host его не копирует.

    По просьбе страницы Host зовёт session/load на живом соединении — только между ходами: тогда всё, что агент шлёт до ответа на load, — повтор, и он идёт только запросившему, мимо модулей и других зрителей. У ленты и у истории одна форма — события ACP.

  • Почему страницы, а не весь повторФайлы разговоров на этой машине: 847 штук, медиана 0,45 МБ, 90-й процентиль 2,1 МБ, 99-й — 18,7 МБ. Телефону — только последние 50 событий; «раньше» — снова load, Host режет.
  • Замер на живом флотеВремя повтора и байты на открытие чата — в журнале Host. Тюнинг — потом, по замеру.
  • Те же параметрыАдаптер Claude сверяет параметры load с живой сессией; при других — разбирает её и собирает заново, идущий ход пропадает. Поэтому папка, MCP и _meta уходят агенту только при запуске, load и resume несут их же, новые — только перезапуском между ходами.
  • Лимит loadКак у initialize. Не уложился — процесс убит, дальше ветка «процесс вышел»: иначе хвост повтора ушёл бы модулям.

    Два флота на одном компьютере

    Компьютер входит в два флота сразу — например, в тестовый и в рабочий. Каждый флот ставит свою службу keeper со своей папкой данных; дальше каждая служба держит свой Host, свои сессии и свои аккаунты и ничего не знает о второй. Включается одним именем при установке: keeper install --name prod. Без имени всё как сейчас.

    чтоу каждой системы своёобщее
    служба ОСswitchboard-keeper · switchboard-keeper-prod
    папка данныхфайл keeper, план, пропуск машины, хранилище Host, держатели, аккаунты, слоты, части
    Host и сессиисвой Host, свои позывные; порт MCP выбирает ОС при первом запуске, он лежит в хранилище
    агентывход Claude — в аккаунтах своей системы; Codex — своя CODEX_HOME с входомпапка Claude для сессий без слота, вход Gemini

    По коду сейчас все данные keeper и Host лежат в одной папке, она задаётся SWITCHBOARD_HOME. Мешают двое: имя службы зашито одно, и служба не знает папки. Второй keeper install сегодня отказывает: «keeper уже стоит службой».

  • Имя — одно правило у keeperИз --name keeper выводит имя службы и папку и запускает себя командой run --name prod. Host и держателям папку передаёт в SWITCHBOARD_HOME — они её не выводят.
  • Обновление и удалениеkeeper обновляет файл в своей папке; keeper uninstall --name prod снимает только свою службу.

    • A2A — только на границе флота

    A2A — открытый стандарт, по которому агенты разных систем дают друг другу задачи: у агента есть визитка с умениями, задача идёт по шагам «работает → ждёт ввода → готово», поток — по SSE. Внутри флота он не нужен: сессии уже говорят друг с другом через флот. Нужен он только на границе — когда агент другой системы зовёт сессию флота или сессия зовёт его. Выберите направление.
